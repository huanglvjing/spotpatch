# Next.js 构建转换与源码定位

## 责任边界

本文只定义 Next 构建器如何承载通用 source transform。marker 属性、marker 值格式、intrinsic JSX 判定、已存在 marker 的处理和精确行列语义仍引用现有唯一规范 (见 doc-id:04-vite-plugin)；源码来源与置信度 (见 doc-id:06-source-resolution)。公共编译内核抽取完成后，应把这些共同事实迁移到新的公共内核规范，并让 Vite/Next 同时引用，不能复制两份。

## 选择 Loader，而不是 Compiler 私有插件

- Turbopack 官方支持一部分 webpack Loader，但不支持 webpack Plugin。
- Next SWC Plugin 仍具有实验性和 WASM/版本维护成本。
- 自定义 Babel 配置会使项目退出默认 Next SWC；SpotPatch 不应改变宿主编译器选择。
- 现有 Oxc + MagicString transform 已能保持源码格式和高精度 map，抽成 Loader 的风险低于重写两套编译插件。

因此规划发布一个由 `@spotpatch/next` 内部引用的 Loader entry；实际 AST 行为只来自 `@spotpatch/compiler` (见 doc-id:next-02-package-architecture)。

## Turbopack 输出契约是阻断项

现有 SpotPatch transform 只给 JSX/TSX 增加 marker，输出仍可能包含 TypeScript 和 JSX；而 Turbopack 官方只接受 Loader 返回 JavaScript。不能仅凭 webpack Loader API 兼容就推断 Next 的内置 SWC 会在正确阶段继续处理该输出。

Gate N1 必须用真实 Next 15/16 fixture 证明以下任一成立：

1. SpotPatch Loader 在 `turbopack.rules` 中返回带 marker 的 TSX/JSX 后，借助受支持的 `as`/规则链仍会进入 Next 内置编译，并保持 Fast Refresh 和 source map；或
2. 官方支持的规则顺序允许 SpotPatch 接收/返回已编译 JavaScript，同时仍能可靠识别业务 JSX 的原始行列。

两者均不成立时 ADR-025 视为被否决，必须回到编译入口架构评审。禁止在未评审情况下自行转译 TypeScript/JSX、复制 Next SWC 配置、使用私有 Turbopack API，或发布 webpack-only 版本后声称完整 Next 支持。

### Gate N1 本地实测进展

2026-08-09 的隔离实验在 macOS arm64 上验证了 Next 15.3.9/React 18.3.1 与 Next 16.3.0/React 19.2.8：不设置 `as` 时，返回仍含 TypeScript/JSX 的探针 Loader 在两版 Turbopack 中继续进入 Next 内置编译；对应 webpack `enforce: "pre"` 通道也通过 hydration、Fast Refresh、Edge 和 map 断言。该结果只证明锁定版本的本地编译链，不改变官方“Loader 返回 JavaScript”的公开约束，也不外推到其他 Next 版本。

实验同时证明两种构建器的 map source 基准不同：webpack 探针使用项目根相对 source，Turbopack 探针使用资源相对 source 后再由 Next 合成 indexed map。该差异属于 Adapter 翻译层，不能写进公共 compiler。唯一实验结论、复现命令和剩余阻断见 `experiments/next-adapter/CONCLUSION.md`；Ubuntu 与多 worker 压力证据未完成前，本节结论仍为 `blocked`，ADR-025 保持 Proposed。

## 编译阶段

### webpack 通道

- 仅在 `dev === true` 时追加 `enforce: "pre"` rule。
- rule 在客户端、Node server、Edge server 三类编译中保持幂等，以便 Server Component host JSX 也获得 marker。
- 不覆盖 Next `defaultLoaders`、devtool 或 React Refresh loader。
- Loader 返回 `code + source map`，并把输入 map 与自身 map 正确串联；不得返回 `null` map。
- 同一配置对象被多次包装时通过私有 `Symbol`/可验证 rule identity 防止重复追加，不使用脆弱的 loader 路径字符串猜测。

### Turbopack 通道

- 使用 `turbopack.rules`，匹配受支持的 JSX/TSX 文件并排除 foreign/package output。
- Loader options 只能包含 plain primitive/object/array；公共 `RegExp` filter 必须序列化为受控 `{ source, flags }` 结构并在 Loader 内重建，不能直接传递实例。
- Loader options 必须包含本次 CLI 启动生成的非敏感 `registryEpoch`，使 Turbopack/webpack 持久 cache 不会在新 Session 复用旧 fileId；epoch 不是认证凭据。
- 不依赖 Turbopack 未实现的 `emitFile`、`loadModule`、`importModule` 或完整 `fs` LoaderContext。
- 官方契约仍按 Loader 返回 JavaScript 理解；锁定版本下“无 `as` 返回 TSX 后继续进入内置编译”的实测行为必须由兼容矩阵持续守护，不能外推。跨平台 HMR/map 复跑与显式多 worker 压力证据仍是 POC 阻断项 (见 doc-id:next-08-testing-delivery)。

## 文件过滤

Next Adapter 在调用公共编译器前完成框架 ID 归一化：

1. 取得 Loader `resourcePath` 的真实绝对路径。
2. 拒绝 root 外路径、符号链接逃逸和 NUL。
3. 只处理公共 include 且不匹配 exclude 的扩展名。
4. 固定排除 `.next`、`node_modules`、SpotPatch 包产物、Next 内部生成模块和测试/故事/覆盖率产物。
5. 不按模块内容推断 Server/Client Component；符合条件的 host JSX 都进入同一 transform。
6. 只以 `<` 快速跳过明显无 JSX 文件，不能把它作为正确性判断。

Next 新增排除项只能在 Adapter 翻译层定义；共同排除与公共选项继续由公共配置维护 (见 doc-id:03-public-api-models)。

## Source Registration

Vite 插件可在同进程 Registry 同步登记路径；Next Loader 可能运行于多个 Loader worker，不能共享进程内 Map。规划采用内部注册通道：

1. Loader 使用 Sidecar launcher 只注入到 Node 子进程的内部凭据建立请求。
2. 请求只提交 Loader 的绝对 `resourcePath`；Sidecar重新执行 real root、文件类型、扩展名和过滤授权。
3. Registry 对同一 `registryEpoch + 规范化路径` 在一次 Session 返回稳定 fileId；并发重复登记合并为同一结果。
4. Loader 先成功登记并验证 epoch/fileId，再调用 compiler 注入 marker；禁止先生成 marker 后异步“补登记”。
5. 每个 worker 使用有界 LRU 缓存 `registryEpoch + path → fileId`；Sidecar Registry 仍是权威，不以 worker cache 授权。
6. 注册超时、Sidecar 关闭、epoch 不匹配或响应校验失败时 transform fail-open，返回完全未注入 marker 的原模块并发出一次脱敏警告；不得阻断业务页面，不得产生查无此 fileId 的幽灵 marker，也不得退化为在 DOM 中写路径。

内部通道不是公共 HTTP 协议，不能被 Next rewrite 暴露 (见 doc-id:next-05-sidecar-protocol)。请求数量、冷启动成本和 worker 复用必须实测；若达不到预算，应优化批处理/缓存，不能放宽路径安全。

## Server Component 与 Client Component

Loader 对两类模块都只修改 intrinsic opening element，不注入浏览器代码：

```tsx
// Server Component 与 Client Component 均只增加开发期 marker
return <button data-spotpatch-source="session-file-id:line:column">Save</button>;
```

Server Component marker 经服务端渲染进入 HTML/RSC；Client Component marker经 hydration 保持。不得给 composite component 增加未知 prop，不得用 `cloneElement` 或运行时遍历补写 marker。RSC 降级和 React stack 语义 (见 doc-id:next-06-rsc-runtime)。

## Source map 与诊断

- map 必须以原始项目相对 POSIX 路径为 source 并包含原始内容；不得包含 Sidecar临时路径或凭据。
- Loader 合并上游 map，保证 Next error overlay、断点和 Fast Refresh 仍指向业务源码。
- 诊断命名空间区分 `spotpatch:next:webpack`、`spotpatch:next:turbopack` 和 `spotpatch:compiler`。
- 普通模式每个文件/原因只警告一次；debug 可记录耗时和缓存命中，但不得输出源码、绝对路径或内部 token。
- parser/marker 失败一律 fail-open；路径注册安全失败不得伪造 fileId。

## 兼容冲突

下列组合必须有 fixture，不能依赖主观推断：

- 自定义 webpack rules、Babel 配置、MDX、React Compiler、styled-components/emotion compiler 选项。
- `src`/根目录布局、Monorepo 外层 root、symlink workspace 与 `transpilePackages`。
- `next/image`、`next/link`、Portal、lazy/dynamic、Suspense、RSC 导航。
- Windows 盘符/大小写、POSIX 路径、查询后缀和虚拟模块 ID。
- HMR 行号变化、文件重命名、删除、Registry 失效、Sidecar 崩溃、Next dev cache 与 CLI Session 重启。

未通过组合应显示为明确“不支持/冲突”，禁止静默跳过后仍显示 exact。
