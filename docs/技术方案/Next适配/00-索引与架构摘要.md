# Next.js 适配索引与架构摘要

## 文档状态声明

本目录描述 SpotPatch Next.js 适配的活动架构与 0.x 公共预览实现，不是“已经正式支持 Next.js”的声明。`implementation-status: public-preview` 表示 `@spotpatch/next@0.1.0` 已作为可安装的 npm 公共预览分发，但尚未完成 Gate N4 的全部版本、Router、Node、OS 与浏览器交互矩阵。只有正式支持门禁全部通过后，产品支持矩阵才能从“不支持”改为“正式支持” (见 doc-id:01-product-boundary)、(见 doc-id:next-08-testing-delivery)。

当前 `@spotpatch/vite` 的既有支持声明不变；Next.js 用户可以从 npm 安装 `@spotpatch/next` 公共预览，但不得把 `@spotpatch/vite` 当作 Next 插件，也不得把包可安装性等同于正式兼容或生产支持。

## 编码前复核结论

2026-08-09 已完成 Gate N0、锁定版本 Loader POC、公共 `compiler`/`dev-server` 抽取和一个 Next 16.3/React 19.2 App Router 公共预览宿主。正式链路已经覆盖 CLI/config 配置请求、Sidecar、source registration、Turbopack/webpack Loader、bootstrap、Runtime UI、源码上下文和生产 noop；Vite 仍使用同一公共实现并通过回归门禁。

仍然阻断正式支持的事实包括：

- external rewrite 的 NDJSON 流、取消、复杂 `basePath`/`trailingSlash` 与自定义 matcher 组合尚未完成 required fixture。
- React Adapter 对 React 19 Fiber 语义仍返回受控降级；marker、DOM、UI 可用不等于完整 React 19 组件栈支持。
- Pages/hybrid Router、Next 15 维护线、Windows、Node 20/22/24 和复杂宿主配置尚未跑完正式矩阵。
- 私有宿主 Runtime POC 已通过两种构建器的按钮交互与源码上下文断言，但尚未覆盖完整编辑器/Agent 链路和 required 浏览器矩阵。
- 默认 Turbopack 历史 Loader POC 生产构建已通过 marker/环境键扫描；正式适配器仍缺完整 Turbopack 生产零残留 fixture，不能以该局部结果或 webpack 结果替代。

因此 0.x 公共预览必须继续保留醒目警告并补齐门禁；在门禁完成前不得修改产品支持矩阵或发布稳定支持声明。具体证据与缺口 (见 doc-id:next-08-testing-delivery)。

## 仓库决策

不创建第二个 Git 仓库。当前实现已在现有 Monorepo 增加 `@spotpatch/next`，并把 Vite/Next 共用的源码转换和开发服务能力抽成 `@spotpatch/compiler` 与 `@spotpatch/dev-server`。原因和包依赖边界 (见 doc-id:next-02-package-architecture)，正式 ADR (见 doc-id:15-risks-adr)。

仓库边界与 npm 边界不是同一个概念：

- 一个 Git 仓库维护共同协议、Runtime、Agent、安全规则、测试和版本图。
- 每个框架保留独立用户入口包；Vite 用户安装 `@spotpatch/vite`，Next.js 用户安装 `@spotpatch/next`。
- 用户不需要手动安装内部公共包；发布图必须闭合。
- 框架适配器不得相互依赖，Next 适配器不得通过安装 Vite 来复用实现。

## 目标架构摘要

```text
Next source modules
  → SpotPatch loader（Turbopack / webpack）
  → internal source registration（registry epoch）
  → source marker
  → Next rendered HTML / RSC payload / hydrated DOM
  → @spotpatch/next/client（pre-hydration hook）
  → @spotpatch/runtime
  → same-origin /__spotpatch/v1/**
  → Next beforeFiles rewrite
  → loopback-only SpotPatch Sidecar
  → source/editor/Agent/Git/provider core

spotpatch-next dev
  → local Next child + authenticated loopback configuration
  → withSpotPatch resolves development config
  → owner configures the single Sidecar
```

该图只说明责任流，不重复 marker、HTTP endpoint、Agent 工具或公共配置的定义；这些事实继续分别由现有主题文档管理 (见 doc-id:03-public-api-models)、(见 doc-id:09-local-protocol-security)。Next 专属承载方式由本目录子文档定义。

## 核心工程判断

- Next 16 默认 Turbopack，因此只支持 webpack 不构成正式 Next 支持。
- Next 默认存在 Server Component，浏览器 Fiber 不能完整表达服务端组件树；精确 host marker 是主链路，React Adapter 只能增强。
- Bippy 必须在 React hydration 前安装 hook；使用 Next 官方 `instrumentation-client`，不能等待页面挂载后再初始化。
- Next 没有 Vite `configureServer` 等价公开钩子；本地文件、编辑器和 Agent 能力由独立 loopback Sidecar 承载。
- Sidecar 绑定 loopback 不足以抵御 Next external rewrite；首版 Next child 也必须强制 loopback，明确不支持 LAN。
- 父 CLI 不重复求值 `next.config` 或复制 Next `.env*` 规则；开发配置由真实 Next求值后经独立 secret 认证的 loopback内部请求配置唯一 Sidecar。
- 持久构建 cache 不能复用上一 CLI Session 的随机 fileId；非敏感 registry epoch 是 Loader cache identity 的组成部分。
- 不占用面向部署平台的 `adapterPath`，不使用会削弱 Next 优化的 Custom Server。
- 生产零残留是正式支持条件；0.x 公共预览也不接受仅靠 `NODE_ENV` 运行时判断的“代码存在但不执行”。

上述判断对应的证据、细节和替代方案均在子文档及 ADR 中追溯，本文不维护第二份实现规则。
