# 外部 Agent 连接：安全、隐私与权限边界

## 安全结论

Generic MCP/CLI Inbox 仍限制为“读取用户已明确发布、且由 Node 重新授权的有界上下文”，不授予文件、Shell、Git、网络或模型权限。

主动模式分成两条明确权限边界：Claude attached adapter 只向外部宿主注入事件，SpotPatch 不拥有其写入、checks 或回滚；ADR-037 Codex managed adapter 只写 SpotPatch 创建的独立临时快照，并在显式 checks 通过后由 SpotPatch 冲突安全回写。`externalAgent: true` 本身只启用 dev-only Inbox/Broker/控制面，绝不能静默获得 `managed-apply-v1`；首次扩大权限仍需浏览器之外的本地确认。

## 信任边界

| 主体 | 信任程度 | 能力 |
| --- | --- | --- |
| Runtime/页面请求 | 不可信输入 | 只能提交有界 annotation/cursor；无 root、命令、bridge token |
| SpotPatch dev-server/Sidecar | 可信策略执行者 | Source Registry、root、当前源码、Store、token 和 Broker |
| MCP/CLI Connector | 受控本地依赖，但输入/输出仍校验 | 读取安全发现文件并访问匹配 Broker；无写项目能力 |
| Attached Connector/Adapter | 用户显式启动或启用的高权限本地进程 | 持有一个 dev Session 的唯一受管 lease；按固定宿主协议触发宿主 writer，SpotPatch 不接管其工作区 |
| Managed Supervisor/Adapter | dev 生命周期内的受控本地进程 | 固定 grant/profile 下启动 App Server；只把独立快照交给模型写，由 SpotPatch 审计和回写 |
| Agent host/模型 | 外部系统、不可信执行建议 | 获得交接后使用自身权限；内容可能传给第三方 Provider |
| LAN/其他网站 | 不可信 | 不应接触 Broker；浏览器 API 继续受 token/Origin 限制 |
| 其他 OS 用户 | 不可信 | 由文件 owner/ACL 和 loopback token 隔离 |
| 同一 OS 用户下的恶意进程 | 不在首版可防御边界内 | 该进程通常已能读用户项目与进程文件；文档必须如实说明 |

同源项目脚本若已获得 browser session token，现有本地 API 无法从服务器端证明点击来自真实用户。Shadow DOM 和显式按钮主要防止误操作，不是对恶意同源脚本的可信 UI 证明。若未来要对不可信页面代码提供强同意，需要浏览器扩展/native host 等新的信任根，不能在当前网页 Runtime 中假装解决。

## 主要威胁与控制

| 威胁 | 控制 |
| --- | --- |
| 页面伪造 path/root/源码 | 请求只接 annotation；Source Registry + realpath + 当前文件重读；全有或全无 |
| 点击误选导致无意发送 | 选择与发送分离；预览；每次明确按钮/快捷键；首次会话披露 |
| LAN 访问 connector endpoint | 专用 listener 只绑定字面 127.0.0.1；remote address/Host/token 三重校验 |
| 浏览器窃取 bridge token | token 不进入 HTML、Runtime、公开 endpoint、日志或 capability；发现文件用户私有 |
| Agent connector 窃取 browser token | 双 token 域；Broker 不接受 browser token，描述符不含它 |
| DNS rebinding/代理/redirect | endpoint 必须是字面 loopback；Connector 禁用 proxy、redirect 和自定义 URL |
| 伪造/符号链接发现文件 | owner/ACL、普通文件、no-follow、大小、Schema、projectKey、Broker handshake 全校验 |
| 崩溃留下源码 | 正文只在内存；发现文件无项目内容；陈旧描述符有界清理 |
| Token/PID 复用 | 每 Session 随机 token；sessionId/protocol handshake；不能只以 PID 判断 |
| Prompt injection 来自 DOM/注释 | 工具说明标为不可信数据；instruction 不能覆盖宿主 system/sandbox；无 Connector 写工具 |
| MCP 结果过大导致耗尽/截断 | 发布前集中字节上限；Broker/Connector 双重 Schema/size；整份拒绝，不丢目标 |
| 多项目串读 | MCP roots/cwd 计算 projectKey；精确匹配；歧义失败；不接受模型传 root |
| 多个 Agent 同时取得交接 | UI 提示项目 Inbox 语义和等待者数量；回执不声称唯一消费者 |
| 一次点击触发多个受管 writer | 每 dev Session 单一 active lease + dispatch capacity=1；禁止主动广播、队列和自动 steer。Generic MCP Inbox 仍可被其他宿主读取，用户不得同时武装另一个自动写入会话；跨 dev Session 不宣称全局锁 |
| 网络失败导致重复写 | Runtime requestId 幂等；投递确认不明进入 delivery-unknown；禁止自动重试 |
| 页面扩大执行权限 | Browser Schema 禁止 command/args/cwd/root/thread/model/environment/approval/sandbox/checks；attached 权限来自宿主，managed 权限来自 dev 终端 challenge 和固定 grant |
| 子进程/协议输出注入或耗尽 | 固定 executable/args、`shell: false`、JSONL strict/size limit、stderr 有界脱敏、未知 request fail closed、进程树清理 |
| 外部 Agent 覆盖本地改动 | attached 明示依赖宿主/Git；managed 只写独立快照，apply 前逐文件基线哈希冲突检查 |
| managed 继承用户其他 MCP/hooks/plugins | 独立进程可能绕过模型 sandbox 产生外部副作用 | 项目级私有 `CODEX_HOME` + 固定 process/thread config + `hooks/list`/`mcpServerStatus/list` preflight；不能证明完全隔离时 managed fail closed、降级 Inbox |
| 经典 workspace-write 可读取项目外数据 | 不相关本机内容或认证材料进入模型或命令 | 固定 `spotpatch-managed` permission profile：根默认拒绝、最小系统路径只读、仅精确快照根可写、网络关闭；thread 返回的 active profile 和 workspace roots 必须精确复验 |
| Connector 供应链漂移 | 使用项目锁定依赖/bin；设置禁止无锁定 `npx latest`；发布 provenance/lockfile 扫描 |
| 生产残留 | dev phase 装配；生产 bundle/route/string/port/token 负向扫描 |

## 双认证域

### Browser session token

沿用现有本地协议：只进入开发页面的 SpotPatch Runtime 和同源请求头，配合 Origin/Fetch Metadata。它只能发布和查询 Summary，不能读取 Broker 正文或发现文件。

### Bridge token

- 每个 dev-server Session 生成至少 128 bit CSPRNG 随机值；
- 只存在 Node 内存和权限受控的发现描述符；
- 只授权该 Session 的 Broker；不能列出其他 projectKey；
- 不接受 query string、cookie、URL userinfo 或 CLI 参数传递；只放固定 header；
- 比较使用 constant-time；失败响应不区分 token 不存在/错误；
- 开发服务重启立即轮换，旧 token 不可恢复；
- 任何日志、错误、MCP result、CLI JSON、core dump fixture 和测试 snapshot 都不得包含真实 token。

首版不把 bridge token 当成能抵抗同一 OS 用户恶意进程的高强度 secret；它的目的主要是隔离 LAN、其他网页、陈旧端口和其他 OS 用户。

## Loopback Broker 硬要求

- 使用独立随机端口，只绑定 `127.0.0.1`。若未来启用 `::1`，必须独立监听并验证 remote address，不使用 `localhost` 隐式解析。
- 启动后从实际 socket 地址读取端口，再发布描述符；禁止“找空闲端口后关闭再重开”的 TOCTOU。
- 只接受固定 path、POST 和 JSON；body parser 在分配大对象前执行字节限制。
- `Host` 只接受 `127.0.0.1:<actualPort>`；拒绝绝对 URL request target、upgrade、CONNECT 和代理 header。
- 不配置 CORS；浏览器不应调用。额外检查 `Sec-Fetch-Site` 时不能替代 token。
- 响应 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff`，不反射 Origin。
- 请求、waiter、header、socket idle 和关闭均有上限；dispose 主动 destroy 残余 socket。
- 不信任 `X-Forwarded-*`，不跟随 redirect，不监听 Unix wildcard 或 LAN interface。

## 发现文件安全

实现时必须抽象跨平台安全文件接口，并通过真实 OS 测试：

- 打开目录和文件时拒绝 symlink、directory/junction/reparse point 等非普通文件；
- POSIX 校验 `uid === process.getuid()`，目录不能 group/world 可写，文件 mode 不宽于 `0600`；
- Windows 校验当前用户拥有且 ACL 未给 Everyone/Users 写入或读取；仅“路径在 LOCALAPPDATA”不是证据；
- JSON 体积使用很小的固定上限，字段 strict，endpoint 只允许字面 IPv4 loopback 与合法端口；
- 只扫描集中上限内文件，超出时诊断并 fail-closed，避免目录耗尽攻击；
- 清理陈旧记录前重新 lstat/owner/Schema，且只删除精确 Session 文件，不递归删除整个运行目录；
- 设置/卸载命令不能把发现目录加入项目、同步盘或版本控制。

## 数据最小化与生命周期

### 发布前

- UI 列出数据类别、目标文件和目标数量；源码/DOM 预览复用现有安全展示。
- 第一次外部发送在当前开发 Session 内显示披露：任何连接到本项目的 Agent 都可能读取，且其 Provider 可能把上下文发送到第三方。
- 同意不写 localStorage、不跨开发服务 Session、不替代每次“发送”动作。

### 存储期间

- 完整 snapshot 只在 dev-server 内存；不写发现文件、日志、诊断、MCP 配置或历史数据库。
- 只保留一个 current 正文；旧 revision 仅留有界 Summary。
- TTL 和响应预算由 (见 doc-id:external-agent-07-ux-performance-observability) 唯一定义。
- 内存删除表示解除引用并允许 GC，不能宣称覆盖了堆、swap、崩溃转储或宿主进程快照；这是 JavaScript 运行时的真实限制。

### 交付后

- Connector 可以把 snapshot 返回 Agent host；SpotPatch 无法控制 host 是否写聊天历史、索引项目或发送远程模型。
- UI 和文档必须链接到用户所选 Agent/Provider 的数据政策，而不是给出 SpotPatch 保证。
- 首版不记录 Agent 产品名、账号、模型、对话内容、工具调用或文件修改。

### 失效与退出

- TTL 到期、显式清除（若后续 UI 提供）或 Manager dispose 立即使正文不可读取并取消 waiters。
- 描述符正常退出删除；崩溃记录不含项目内容，但 Connector 仍应在验证不可达后有界清理。
- 页面关闭不立刻删除交接，因为 Agent 可能正在取用；dev-server 才是 Session owner。

## Attached 外部执行权限声明

Generic/attached 外部 Agent 修改代码时：

- 使用 Agent host 自己的 cwd、workspace trust、sandbox、tool approvals、Git 状态和网络策略；
- SpotPatch Connector 没有建立 worktree、基线 hash、保护路径、checks、Diff 或 Revert；
- `picked-up` 不能证明 Agent 读取当前文件，更不能证明修改正确；
- 用户应依赖 Git、Agent 审批和项目测试检查变更；
- 若产品需要 SpotPatch 统一审阅，应该把交接输入导入现有内建 Agent Job，而不是给 Connector 增加无边界写工具。

内建 Agent 的隔离与 Apply/Revert 规则见 (见 doc-id:16-ai-agent-execution)，不能通过引用其文档扩大 Generic/attached 承诺。managed Codex 只有满足下节机械门禁的部分才可声明 SpotPatch 审计。

### ADR-036 Attached/旧 Connector 的最小权限

- Claude Channel adapter 只向用户已启动并显式启用 Channel 的会话写事件；不声明 permission relay，不传远程审批，不启用 `--dangerously-skip-permissions`。Claude 的项目 trust、Write/Edit/Bash 审批仍由 Claude Code 决定。
- Codex adapter 必须在 dev Session 的精确 canonical 项目根启动。主动 `connect` 不读取、不创建也不修改项目 `.codex/config.toml`，而把由框架类型决定、用户参数不可覆盖的 SpotPatch MCP command/args 和固定运行目录环境变量名称白名单注入专用 App Server thread；持久 `setup --client codex` 仅用于可选 Inbox。这样消除首次连接写配置、TOML 合并和并发覆盖风险，也不把已有项目配置当作 SpotPatch 所有。
- Codex adapter 在用户启动的可信终端中从 PATH 解析 `codex`，立即 realpath 为绝对 executable，验证普通可执行文件、最低稳定版 `0.149.0`，并默认拒绝位于项目 root 内的二进制；同一绝对 executable 必须先在用户配置隔离的私有临时目录生成 experimental App Server Schema，固定请求/通知方法子集完整才继续，随后参数固定为 `app-server`，使用 `spawn(absolutePath, ["app-server"], { shell: false })`。未来版本没有静态上限，但 Schema 与运行时 preflight 任一失败即 fail closed。诊断只显示经用户启动即可获知的 path/version，不记录环境值；浏览器不能覆盖，SpotPatch 也不安装或改写用户 Codex。
- Codex workspace-write 必须通过终端 `--allow-workspace-write` 明确同意；canonical cwd 是唯一运行时 workspace root，App Server 归一化后返回的附加 `writableRoots` 只允许 `[]` 或同一 canonical root，若可选 `runtimeWorkspaceRoots` 存在则必须精确等于该 root。network 默认 false，不使用 danger-full-access。workspace-write 约束写入范围，不声称屏蔽项目外所有读取；network false 只作用于 sandbox 内模型命令，不是对 App Server、模型 API 或独立 MCP server 的全进程断网。
- Codex 首版固定 approval policy `never`：不展示 approval prompt，Codex 只在既有 sandbox 内 best effort；不得把它描述为自动批准，也不能承诺所有越界动作以同一种错误失败。命令/文件/permission/MCP elicitation 等已知反向 request 必须按各自响应 Schema `decline` 或 `cancel`，未知 method 才返回协议错误。
- App Server 可能在 `thread/start` 解析可写 cwd 时把 project trust 持久写入用户 Codex `config.toml`。终端启动披露必须把它作为 `--allow-workspace-write` 的已知外部副作用，真实 POC 保存前后差异；浏览器不能触发或隐藏这一步。
- App Server 仍按 Codex 自身配置分层启动用户已启用的其他 MCP server；SpotPatch 只覆盖 thread 内同名 `spotpatch` entry，不尝试禁用用户的无关 MCP。终端必须披露这一点，因为 sandbox command 的 `network=false` 不约束这些独立进程。
- SpotPatch 不转发 Connector 完整环境，也不向配置写入显式环境值。Codex 持久 Inbox 和主动 inline MCP 只请求按名称转发 `XDG_RUNTIME_DIR`、`TMPDIR`、`TMP`、`TEMP`，使其与 Broker 发现算法的运行目录输入一致。值只在本机进程环境中传递，不打印、不持久化、不进入 Handoff；Browser/Handoff 不能覆盖或扩展列表。增加新名称或显式值仍需独立安全评审。
- Codex turn 摘要中的源码位置只接受规范化的项目相对路径；绝对路径、Windows 反斜杠/盘符、`.`/`..` 段、空路径段和控制字符在 `turn/start` 前拒绝。该限制不能被 workspace-write 的写入边界替代，因为后者不承诺阻断项目外读取。
- POSIX 上 Codex App Server 使用独立进程组，关闭时按整组 `SIGTERM` 后超时 `SIGKILL`；已有子孙进程拒绝 `SIGTERM` 的自动化清理证据。Windows 目前只有 child 终止回退，进程树清理和 ACL 证据均为 `not-tested`。
- 主动 adapter 的 `completed` 只表示宿主 turn/显式上报结束。SpotPatch 不扫描 diff 来猜成功，也不自动 commit/reset/revert。

### ADR-037 Codex managed 的最小权限

以下条款取代上节中 Codex “业务仓库直接 workspace-write、用户其他 MCP 可启动、独立终端每次 connect”的目标形态；上节仍用于 legacy Codex attached 和 Claude attached：

- 首次启用只接受固定 `managed-apply-v1`，由当前 dev 终端 challenge 确认并写用户私有 grant；无 TTY、grant 权限过宽或 project key 不匹配时只保留 Inbox；
- 每 revision 使用系统临时独立 Git 快照仓库；`runtimeWorkspaceRoots` 必须精确等于该 canonical 快照根，业务仓库、其 `.git`、用户配置目录和其他项目不能成为 workspace root；
- 使用固定 `spotpatch-managed` permission profile：`:root = deny`、`:minimal = read`、`:workspace_roots "." = write`、network disabled；不向当前 Schema 注入不存在的 `workspaceWrite.readOnlyAccess`，也不挂载业务仓库依赖根；无法证明凭证读取被拒绝的平台不启用 managed；
- approval 固定 `never`，所有已知审批反向请求拒绝/取消，未知 request 失败；不使用 `process/*`、`thread/shellCommand` 或 danger-full-access。仅为请求 beta permission profile 在 `initialize` 声明 `experimentalApi: true`，不因此开放其他 experimental 方法；
- 每个 project key 使用用户私有 SpotPatch 配置目录下稳定、权限收紧的 managed `CODEX_HOME`；同时把 App Server 的 `HOME/USERPROFILE` 指向该目录。它不在业务仓库、任务临时目录或 Agent readable/writable roots 中，不复制用户 `config.toml`、MCP、hooks、plugins、sessions 或日志。稳定目录只为同一 App Server 身份恢复 crash cleanup journal 中的 thread；普通断开保留，显式撤销 grant 时只删除该 project key 的精确目录；
- 文件型 Codex 登录只在验证 owner、普通文件、私有权限和大小上限后，以不读取内容的 opaque filesystem link 提供给 managed `CODEX_HOME`，仍由 Codex 读取和刷新；Browser、grant、日志和状态协议都拿不到凭证值。只有 keyring 且无法在隔离 home 证明认证时返回 `AGENT_AUTH_REQUIRED`，不得回退到用户原始 `CODEX_HOME`；
- 空表 override 会按配置键合并，`mcp_servers={}` 本身不能证明清除用户 MCP，因此不得把它单独当隔离证据。managed App Server 必须从上述空白 home 启动，再叠加固定 process/thread config，并在每个 thread 的 turn 前要求 `hooks/list` 无 hook/warning/error、分页 `mcpServerStatus/list` 无任何 server；任一方法缺失、Schema 不符或返回非空时均返回 `CODEX_CONFIG_ISOLATION_UNSUPPORTED`，不得开始 turn；
- plugins/apps 在空白 home 上由固定 feature flags 关闭，不调用仍标 under-development 的 `plugin/list` 冒充稳定证明；扩大 Codex 版本范围前必须用生成 Schema 和真实 POC 重新证明。项目自身工程规范仍由任务契约按受控路径读取，不通过复制用户插件实现；
- 环境变量只转发集中 allowlist 中的厂商认证、标准代理和平台临时目录变量，不继承完整环境，不写入项目/grant，不输出值；loopback 强制直连；
- `allowedPaths` 只包含 Source Registry 重新授权的现有源码文件；新增、删除、越界、manifest、lockfile、环境、Git 元数据和工具缓存变化全部拒绝；
- 只运行可信项目配置中显式 required checks；`not-configured/unavailable/failed` 均 `review-required` 且不回写；
- apply 前后执行基线/结果哈希和 change-set 一致性校验；部分写入按匹配哈希补偿回滚，不声称崩溃事务原子性；
- 每 revision 新 thread，终态 `thread/delete`；仅在用户私有 cleanup journal 保存待清理 opaque id，不保存源码、Prompt 或绝对路径。

### 单 writer、幂等与不确定结果

- 同一 dev Session 只有一个高熵 active lease；kind 字符串和 `connectorInstanceId` 都不是身份或认证凭据，所有上报还必须持有私有 lease token。同 kind + 同 instance 的 claim 重试只刷新租期，并返回原 lease token 与原 baseline；不同 kind/instance 冲突失败。
- 每次 Browser 点击使用随机 requestId；同 ID/同正文返回原发布，同 ID/不同正文拒绝。requestId 只解决 Browser→Broker 重复提交，不宣称跨宿主 exactly-once。
- active dispatch 未终止时第二次发送服务端拒绝；UI 禁用只是辅助，不能替代服务端检查。
- `queued` 尚未开始厂商写入时断线可以判 `failed`；transport write/turn request 是否已生效不明时只能判 `delivery-unknown`。未知状态使 Registry 保持 blocked、停止并释放 writer，不重试、不换另一个 adapter 自动执行。
- 用户必须通过精确 cursor 的浏览器确认动作声明“已核对工作区”；该动作只清除内存 hazard，不重发旧任务、不自动恢复已退出 Connector。dev-server 重启会丢失该内存 hazard，SpotPatch 仍须提示用户自行核对，不能把重启说成安全恢复。
- lease 过期、dev-server 重启或 Connector 重启后不重放仍在 TTL 内的旧任务；用户核对当前工作区后，重新连接主动 adapter，并以新的真实点击创建新请求。

## 多 Connector 隐私语义

Generic MCP Handoff 是“本项目 Agent Inbox”，不是加密发给某个厂商。任何当前用户启动、配置了同一项目 SpotPatch MCP 的 Connector 都可以在 TTL 内读取。由于标准 MCP 不提供可验证的对话身份：

- UI 不提供看似安全但可伪造的“只发给 Claude/Cursor/Codex”ACL；
- 用户在哪个 Agent 中调用 get/wait，通常就是实际消费者；
- 若多个 Connector 同时 wait，它们都可能收到；UI 在发送前显示有界等待者数量；
- `pickupCount` 表示取得次数，不显示或长期记录客户端指纹。

主动模式不复用该广播语义：Broker 只允许一个 adapter lease，Runtime 只能看到脱敏 kind/status，不能提交自报 audience。未来若厂商 API 提供受认证的会话身份，可以在专属 adapter 中增加 audience，但不能把命令行 `--client codex` 当安全凭据。

## 安全配置边界

可信项目配置仍只增加 `externalAgent?: boolean`，默认 `false`；字段精确定义见 (见 doc-id:external-agent-04-handoff-protocol)。它只创建 dev-only Handoff/Broker/控制能力。attached 执行必须由外部宿主显式启用；managed 执行必须有固定用户级 grant。两者都不增加能被页面内容控制的公共权限配置。MCP resource/prompt、集中 limits 和设置 UI 行为保持内部受控能力，也不预留未消费字段。

禁止公共配置接受：

- bridge token、固定端口、任意 bind host、远程 URL；
- shell command、CLI args、环境变量 map、任意认证 header；
- 绝对 root、额外 allowlist path、全局临时目录；
- “auto approve / full access / bypass sandbox”；
- 把 snapshot 上传到第三方的 webhook。

## 安全验收

发布前必须至少证明：

1. LAN 请求即使知道端口也因 listener/remote/token 失败；
2. 页面持有 browser token 仍不能访问 Broker，Connector 持有 bridge token 仍不能调用浏览器写接口；
3. 跨项目 cwd/root、篡改 projectKey、伪造 endpoint、symlink 描述符和宽权限文件全部失败；
4. snapshot 与绝对源码路径在 stdout/stderr、错误、测试快照、发现描述符和生产 bundle 中均为零；browser token 不进入描述符，bridge token 只允许出现在 Node 内存和私有描述符，所有 token 在 stdout/stderr、错误、测试快照和生产 bundle 中均为零；
5. 超限 JSON/header、slow body、并发 waiter、连接中断和 dispose 不造成资源泄漏；
6. source stale、symlink source、root escape 和浏览器伪造 code excerpt 被 Node 拒绝；
7. Prompt injection fixture 不能使 Connector 暴露写/Shell 工具或隐藏外部权限提示；
8. Windows ACL、POSIX mode 和 macOS 临时目录在 required OS 上均有真实证据；
9. 生产构建和 `next start` 不监听 Broker、不写描述符、不包含 endpoint 路径；
10. 文档、UI 和发布说明区分 Generic/attached 与 managed；只有 managed 且 Gate 完整时显示 SpotPatch 审计/验证结果。
11. 同一 requestId 并发提交只产生一个 revision/dispatch；同 ID 不同正文、busy 第二次发送和第二个 active lease 均 fail closed；
12. Claude 事件只含 cursor 引用且无 ACK 时不显示 working/completed；Codex 状态只接受匹配 thread/turn 的结构化事件；
13. App Server malformed/oversized JSONL、未知 server request、子进程退出、信号取消和 lease 超时不泄漏正文/token，也不残留 listener/timer/process；
14. Browser 无法通过任何字段改变 executable、args、cwd、root、thread、model、network、approval 或 sandbox，主动模式不使用 shell/danger-full-access/自动权限批准。
15. managed 故意创建 `.pnpm-store`、修改 lockfile/越界文件、启动额外 MCP 或读取 permission profile 拒绝路径时，业务仓库保持不变且任务不能 completed；
16. 无 required checks、检查不可用/失败、原文件并发修改和 apply 故障注入均不覆盖用户内容，补偿回滚只处理本任务且匹配期望哈希的文件。
