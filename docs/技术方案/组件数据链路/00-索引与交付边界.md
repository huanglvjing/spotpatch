## 规范优先级

1. 已生效的核心活动规范仍优先于本专题未落地的候选规则。
2. 本专题内部冲突时，按上表中的唯一维护位置裁决。
3. 若实现需要修改公共模型、endpoint、安全边界或产品承诺，先把最终决定迁入对应核心活动规范，再编码。
4. `18` 只保留结论和导航，不维护第二份字段定义、错误码或预算。
5. `13` 记录可复核代码事实，不把目标文档的未实现部分包装成现状；实现与硬约束冲突时先停下并记录 ADR。

## 阅读与评审顺序

1. 产品、设计和工程共同评审 `01`、`02`、`08`，确认用户真正看到什么。
2. 编译器、Runtime、服务端负责人评审 `03`–`07`，确认可证明边界和依赖方向。
3. 安全和性能评审 `09`–`11`，冻结数据最小化和测试分母。
4. 特殊客户端/传输适配评审 `14`，确认逻辑调用、物理传输和后端事实没有混写。
5. 最后评审 `12` 的 POC 与里程碑；不得跳过 POC 直接开发完整 UI。

## 规范性关键词

- **必须 / 不得**：硬约束，违反即不能合并或发布。
- **应 / 建议**：默认选择；偏离时必须在 PR 或 ADR 说明理由。
- **可以**：受支持的可选能力，不构成交付承诺。
- **候选**：尚未进入活动公共契约，编码前仍可通过评审修改。

## 核心术语

| 术语 | 定义 |
| --- | --- |
| selected element | 用户在页面上命中的真实 DOM 元素 |
| source component | 经 marker/adapter/registry 证明的业务源码组件 |
| request callsite | 源码中真正创建 HTTP/GraphQL/RPC 请求的调用位置 |
| trigger boundary | click、submit、effect、loader 等业务触发入口 |
| request-origin | 请求由哪个组件/路由/Store 触发 |
| data-fed-by | 哪个响应为选中组件的渲染数据提供来源 |
| observation | 当前页面实际发生过的一次已清洗请求事实 |
| declared dependency | 源码中存在但当前观测窗口未执行的依赖 |
| evidence | 可定位、可复核、带版本与来源的事实依据 |
| unassigned | 已观测请求存在，但没有足够证据归到组件 |
| unknown | 当前授权范围或支持能力内无法证明；不是失败猜测 |

## 交付物边界

专题目标实现由五个可独立验收的产品面组成：

1. 选中组件的请求与数据来源报告。
2. 不要求打开 DevTools 的页面接口总览。
3. 参数名/来源/shape 与响应安全 shape、实际消费字段。
4. 客户端 state/cache/store/storage 以及可证明的同仓服务端持久化。
5. 用户显式触发、只基于准确上下文的 AI 解释与辅助查找（当前 Beta 未实现）。

以下不属于首版：通用浏览器 DevTools 替代品、跨微服务全链路追踪、任意数据库逆向、Worker 内请求、生产环境探针、自动执行接口、修改业务数据、上传原始 payload。

## Gate D0：文档完成判定

- 每个字段、状态、预算和默认值只有一个归属文档。
- “百分百”分母、未知策略和零误归属被明确写入验收规范。
- 登录按钮、微信轮询和三类表格链路均有实仓证据。
- UI 覆盖加载、空、未观测、未归属、截断、错误、敏感、流/Blob 和能力关闭状态。
- AI 输入可预览、可引用、可清洗，且不能把推断变成事实。
- 包依赖、模块接口、配置所有权、清理路径和禁止硬编码规则可执行。
- POC 失败条件、回滚方式和禁止进入公共包的半成品边界明确。
