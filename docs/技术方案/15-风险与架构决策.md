# 风险与架构决策

本文件是风险登记和架构决策记录的唯一事实来源。风险表保留原始处理摘要；可执行细则只以表后引用的主题文档为准，避免维护第二份实现规则。

## 关键风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| React Fiber 字段变化 | 组件名/组件栈失效 | 独立 adapter、版本门禁、AST 主链路不受影响 |
| 第三方组件无业务 host marker | 只能定位库内部 DOM | Fiber 向上寻找业务 composite，显示 probable |
| CSS-in-JS 无原始文件位置 | CSS 上下文不完整 | 输出规则和 computed value，明确 warning |
| 大页面 stylesheet 很多 | 点击卡顿 | 只在选中后采集、缓存 stylesheet 索引、分帧 |
| Vite LAN 暴露本地接口 | 读取源码/打开编辑器风险 | token、Origin、loopback 默认、root allowlist |
| HMR 重复注入 runtime | 重复 UI 和监听器 | Symbol 单例 + 完整 dispose |
| Prompt 过长 | AI 噪声和成本增加 | 分段预算、优先级裁剪、预览 |
| 表单/DOM 含敏感数据 | 隐私泄漏 | 永久密码清洗、默认敏感模式、复制前预览 |
| Key 进入浏览器、日志或检查进程 | 账户与费用泄漏 | Node env Secret Resolver、禁止 `VITE_`、全链路脱敏与泄漏测试 |
| 中转站协议或模型能力名实不符 | 工具循环中断或错误执行 | 显式协议、真实 capability probe、严格事件 Schema、无文本 patch 回退 |
| 中转站跨模型轮次复用 tool call ID | 合法后续调用被误判为重放，或 UI 覆盖早期工具活动 | SpotPatch 轮次作用域幂等键、同轮冲突拒绝、跨轮独立执行、参数/ID 错误分离 |
| 模型能调用工具但不能稳定生成 canonical Git diff | 局部修改反复拒绝直至轮次耗尽 | 既有文件优先使用唯一精确 `replace_text`；复杂结构改动保留 `apply_patch`；两者共享本地安全与 Git 审阅门禁 |
| Prompt injection 或恶意工具参数 | 越权读取、写文件或执行命令 | 上下文全视为数据、本地 allowlist、保护路径、无通用 shell、fail-closed |
| 模型循环、长输出与重试 | 费用、延迟和资源失控 | 轮数/调用/响应/时间硬限制、取消、仅安全阶段有界重试 |
| 脏工作区或并发人工修改 | 覆盖用户代码、错误撤销 | clean 默认、显式纳入同意、隔离快照基线、Agent 触及路径哈希复验、只撤 Agent 增量、冲突拒绝 |
| 第三方中转站保存或转发源码 | 项目数据外泄 | 首次显式同意、最小上下文、明确第三方政策不由 SpotPatch 保证 |
| 多目标上下文放大或异步串位 | Prompt 后续目标丢失、费用放大、错误组件被修改 | 有界目标集、源码坐标去重、逐目标 revision 校验、公平预算和服务端全量重新授权 |
| 多目标共用一段说明 | 不同组件要求被合并、遗漏或错误套用 | `instruction` 归属目标、schema v3、单项/总量上限、Prompt 逐项绑定和原子执行 |
| 语言切换依赖宿主状态或重建工作台 | 接入耦合、草稿/同意/Job 丢失、错误文案混用 | Shadow DOM 内建类型化消息表、显式 locale/切换器、状态与文案分离 |
| 双语工作台与 Agent 交互推高核心 Runtime 包体 | 页面开发启动和解析成本增加、超出既定验收预算 | 完整压缩核心产物，React/Fiber/Bippy 使用独立私有虚拟模块并分别核算 |
| AI 接入要求复制完整 Provider 树 | 新用户误填默认项、把 Key 写入配置、接入与升级成本过高 | 约定式环境、简洁单 Provider API、完整高级 API 三层入口；显式优先且缺项 fail-fast |
| 编辑器命令硬编码、浏览器可选命令或响应过早 | Cursor 无法打开、命令注入或虚假成功 | 受控编辑器枚举、Node 端固定映射、即时启动确认、可见反馈与每次文件重新授权 |
| 推广入口干扰主任务或引入追踪 | 工作台噪声、隐私与供应链风险 | 标题栏克制的官方 GitHub 静态链接、无追踪参数和第三方脚本 |
| Next.js Turbopack Loader API 与版本变化 | transform 失效、HMR/source map 回归或升级即破坏 | 只使用官方兼容层、锁定 fixture、阻断式 POC、版本矩阵与未知版本 fail-fast |
| Next.js RSC 与浏览器 Fiber 信息不对称 | Server Component 名称或完整栈不可见 | host marker 作为精确主链路，Fiber 仅增强并显式降级，不伪造组件语义 |
| Sidecar、external rewrite 与多进程 Loader 注册 | 端口探测、凭据泄漏、源文件授权绕过或开发进程残留 | loopback、浏览器/内部凭据分离、服务端重新授权、生命周期 owner 与协议 E2E |
| Next.js cache、RSC payload 或生产产物残留 | 源码坐标、路径、token 或 Runtime 进入部署 | 开发 phase 才装配、全产物扫描、冷构建复验、失败阻断发布 |
| `next.config`、用户 rewrite/webpack/Turbopack 配置组合 | 覆盖宿主配置、改变顺序或产生静默失效 | 纯包装器、保留同步/异步语义、组合测试、冲突诊断与不破坏式合并 |
| CLI 与 `next.config` 分属父子进程 | 父进程拿不到真实配置/环境，或重复求值配置产生副作用 | Next 真实求值后经私有版本化 IPC 一次配置，等价重入幂等、冲突失败 |
| Next 默认监听 `0.0.0.0` 且 rewrite 可代理 loopback | 局域网设备绕过 Sidecar bind 边界访问本地能力 | 首版强制 Next/Sidecar 双 loopback，拒绝 LAN hostname 与 `allowLan` |
| 持久构建 cache 复用随机 fileId | CLI 重启后 DOM 携带新 Registry 不认识的旧 marker | 每次启动生成非敏感 registry epoch，注册成功后才注入，崩溃整组重启 |
| 当前 React Adapter 实现只识别 React 18.2/18.3 | Next + React 19 安装成功但语义增强不可用 | 实现版本门禁与真实 React 19 fixture 同步升级，未通过前保持 planned |
| 把 MCP resource notification 当成跨客户端主动消息 | 页面显示已推送，但活跃对话没有收到或没有触发模型 | 公共主链路只承诺 get + 有界 wait；主动 channel 必须是经验证的厂商 adapter |
| 外部 Agent 修改被误认为受统一 SpotPatch 保护 | 覆盖本地改动、错误安全承诺、无法撤销 | Generic Inbox 与 attached adapter 只显示宿主证据；只有 ADR-037 managed Codex 使用独立快照、显式 checks 和 SpotPatch 回写 |
| Broker/发现文件导致跨项目串读、LAN 暴露或源码落盘 | 项目内容泄漏、错误会话被修改 | 专用 loopback、browser/bridge 双 token、projectKey 精确匹配、正文只在内存、真实 OS 权限 Gate |
| 主动适配器把一次点击广播、排队或重复执行 | 多 Agent 竞争写、旧上下文覆盖、响应丢失后重复修改 | 每 dev Session 唯一受管 lease、capacity=1、requestId 幂等、busy 拒绝、delivery-unknown 不重试；不冒充跨 Session/Generic 宿主全局锁 |
| MCP 显示 ready 但子进程无法发现目标 Session，或 Agent 整体序列化大型 tool result | UI 长期 working、未执行目标修改、Agent 转入错误自诊断 | 固定运行目录变量名白名单、claim 前 exact-session tool probe、前置有界任务摘要、完整结果按字段投影、结构化终端阶段输出 |
| Browser/DOM 控制本地 Agent 命令或权限 | 命令注入、越权写入、网络/审批绕过 | Browser strict Schema 无执行字段；固定 adapter argv/cwd/profile；终端 challenge 与用户级 grant；无 shell/danger-full-access/自动审批 |
| Codex managed thread 继承用户其他 MCP/hooks/plugins 或默认全盘只读 | 沙箱外副作用、项目外数据进入模型、隔离声明失真 | restricted read roots、project-keyed 私有空白 `CODEX_HOME`、固定 process/thread config、hooks/MCP 零结果 preflight；不能证明时 fail closed 并降级 Inbox |
| 自动猜测验证脚本或无验证直接落盘 | 运行任意生命周期脚本、制造虚假“验证通过” | 只运行显式 required checks；not-configured/unavailable/failed 一律 review-required 且不落盘 |

处理措施的规范位置依次为：React/Fiber 和第三方组件 (见 doc-id:06-source-resolution)、CSS 上下文 (见 doc-id:07-dom-css-collection)、stylesheet 性能与 Agent 验收 (见 doc-id:12-testing-acceptance)、LAN/文件/会话安全 (见 doc-id:09-local-protocol-security)、HMR (见 doc-id:05-runtime-lifecycle)、Prompt (见 doc-id:08-code-prompt)、本地 Agent/Git (见 doc-id:16-ai-agent-execution)、provider/Key/远程数据 (见 doc-id:17-model-provider-credentials)、外部 Agent 交接/连接/权限 (见 doc-id:external-agent-00-index)、(见 doc-id:external-agent-06-security)。

## 架构决策记录（ADR 摘要）

### ADR-001：使用 Vite AST transform，而非修改源文件

状态：Accepted。业务仓库保持干净，HMR 自动更新行号，生产可完全禁用。

### ADR-002：只对 intrinsic JSX 注入属性

状态：Accepted。避免自定义组件 Props、Fragment 和透传行为不确定。

### ADR-003：React Fiber 只作为 adapter 增强

状态：Accepted。Fiber 是私有实现，不作为源码定位唯一依据。

### ADR-004：Runtime UI 使用原生 DOM + Shadow DOM

状态：Accepted。避免嵌套 React root、StrictMode 和业务 CSS 冲突。

### ADR-005：浏览器使用 fileId，不使用路径

状态：Accepted。减少绝对路径暴露，并让服务端拥有最终授权权力。

### ADR-006：v1 本地处理，不接 AI

状态：Accepted for v1；v1.1 可选扩展部分由 ADR-008–012 演进。v1 核心仍先量化定位准确率和上下文质量，AI 未启用或不可用时继续只生成 Prompt，不允许把扩展反向变成核心依赖。

### ADR-007：只发布一个用户入口包

状态：Accepted for Vite v1；多框架范围由 ADR-022 演进。Vite 用户只安装和配置 `@spotpatch/vite`，内部包不成为手动接入步骤。

### ADR-008：Provider-independent Agent Engine 运行在 Vite Node

状态：Accepted。SpotPatch 自己维护统一 Agent 事件、工具和本地执行层；首个 `openai-compatible` adapter 只是可替换的推理连接，不要求 Codex CLI，也不让 provider 获得直接文件或 shell 权限。这样 URL、模型或协议替换不会改变本地授权规则 (见 doc-id:16-ai-agent-execution)。

### ADR-009：凭据只通过 Node 环境变量解析

状态：Accepted。公共配置只保存 `apiKeyEnv`，不接受明文 Key；Runtime 只看非敏感 profile ID/label。v1.1 不提供页面 Key 输入框、任意认证 header 或持久 Secret Store，只允许经过枚举约束的 Bearer 与 `x-api-key`，避免页面脚本和 Vite client env 获得凭据 (见 doc-id:17-model-provider-credentials)。

### ADR-010：协议确定且以真实工具能力探测为准

状态：Accepted，探测触发方式由 ADR-033 补充。完整配置由用户选择 Responses 或 Chat Completions；简洁与约定式配置确定性默认 Chat Completions。SpotPatch 不按错误静默切换，也不因 `/models` 或“OpenAI compatible”标签推断 Agent 能力。只有显式 probe 或真实任务中的固定 function 调用、结果续接和所需流式语义实际通过，才形成 Agent 能力证据；纯文本输出永不自动解析执行 (见 doc-id:17-model-provider-credentials)。

### ADR-011：干净 Git worktree 隔离，review 默认，auto 受硬门禁

状态：Accepted。v1.1 首版拒绝脏工作区，不自动 stash/reset/commit；所有模型写入和检查先发生在 detached worktree。默认展示 Diff 和 checks 后由用户 Apply，auto 仅在配置、安全、规模、检查和基线门禁全部通过时可用；冲突一律拒绝覆盖 (见 doc-id:16-ai-agent-execution)。

### ADR-012：使用双受控写入原语，不把 canonical diff 能力等同于 Agent 能力

状态：Accepted。局部既有文件修改优先通过 `replace_text` 提交“路径、唯一精确旧片段、新片段”，由本地执行器完成内容复验、原子替换、失败回滚和最终 Git Diff 生成；创建、删除和无法表达为单次精确替换的结构改动继续使用 `apply_patch`。`replace_text` 不是任意文本替换或整文件写入接口，两种工具都只能修改隔离 worktree 中允许的文件，并共同接受规模限制、保护路径、checks、Diff 审阅与基线复验。该决策避免把特定模型生成 canonical diff 的稳定性误当作 provider 工具调用能力，同时不扩大模型的文件或命令权限 (见 doc-id:16-ai-agent-execution)。

### ADR-013：多目标作为一个有界、原子的 SpotAnnotation

状态：Accepted。一次用户修改任务只创建一个有序目标集和一个 Agent Job；共享页面环境只保存一次，每个目标保存独立上下文。Runtime 在追加、移除和异步采集时维护逐目标身份，Prompt 按目标公平裁剪，服务端重新授权完整集合并拒绝重复或超限输入。没有采用“每个组件创建一个 Job”，因为该方案会复制页面上下文、增加费用和并发冲突，并使跨组件一致修改失去原子审阅边界；也没有只在 UI 保存数组后继续发送单目标协议，因为那会形成不可见的数据丢失。公共结构和上限 (见 doc-id:03-public-api-models)，生命周期 (见 doc-id:05-runtime-lifecycle)，Prompt 公平性 (见 doc-id:08-code-prompt)，协议授权 (见 doc-id:09-local-protocol-security)。

### ADR-014：修改说明归属目标，废止全局 note

状态：Accepted，替代 schema v2 的全局 `note`。schema v3 把 trim 后非空的 `instruction` 放入每个 `SpotTargetContext`，并记录确定的界面/Prompt `locale`；单项目标和整组任务分别设置公共字符硬上限。工作台使用活动目标折叠编辑器，Prompt 与 Agent 输入把说明紧邻同一目标输出，服务端逐项验证且一次原子执行。没有保留“可选全局说明 + 可选逐项覆盖”，因为两套优先级会产生无法审计的合并语义、空项和漂移；需要跨目标共同约束时，用户应在相关目标说明中分别明确，Agent 不得自行扩大。模型与上限 (见 doc-id:03-public-api-models)，编辑生命周期 (见 doc-id:05-runtime-lifecycle)，输出语义 (见 doc-id:08-code-prompt)，UI (见 doc-id:10-ui-diagnostics)。

### ADR-015：Runtime 自带类型化双语消息，不耦合宿主 i18n

状态：Accepted。Runtime 在 Shadow DOM 边界内维护 `en-US`、`zh-CN` 两套类型完备消息和可见切换器；`auto` 只根据标准文档/浏览器语言选择初值，切换仅替换固定文案与 Prompt 标题，不重建目标、同意状态或 Job。没有接入宿主 React Context、翻译库或 `localStorage`，因为插件可能运行在不同框架、Portal 和未知状态管理环境中，耦合会破坏隔离与确定性。项目数据、代码和 provider label 不做猜测翻译。配置值域 (见 doc-id:03-public-api-models)，视觉和语言行为 (见 doc-id:10-ui-diagnostics)，验收 (见 doc-id:12-testing-acceptance)。

### ADR-016：核心 Runtime 与 React Adapter 使用两个内部虚拟模块

状态：Accepted。核心 `runtime-client` 在发布构建中完整压缩，但把 `@spotpatch/react-adapter` 保持为单一外部导入；Vite 注入插件只为该核心虚拟模块把导入解析到预构建的私有 `runtime-react-adapter` 虚拟模块。adapter 产物独立打包 Bippy 与必要 shared 代码，宿主只安装公开入口 `@spotpatch/vite`，无需直接声明内部依赖。解析条件必须检查 importer，不能改变业务代码对 `@spotpatch/react-adapter` 的正常解析。该方案保留 React 增强与双语 UI，同时让原始核心 Runtime gzip 指标继续按“不含可选 React adapter”的口径真实成立；没有选择提高预算，也没有为了包体删除诊断、翻译或安全能力。构建边界 (见 doc-id:02-architecture-stack)，包体验收 (见 doc-id:12-testing-acceptance)。

### ADR-017：AI 配置采用约定式、简洁与高级三层入口

状态：Accepted。`spotPatch()` 在 Vite Node `config` 阶段只在 URL、模型和 Key 三个必要环境值完整时自动生成单 Provider 配置；`SimpleAiOptions` 允许用户只写 `baseURL`、`model` 和必要覆盖；完整 `AiOptions` 保留多 Provider、多模型和项目 checks。显式 `ai: false` 或显式对象优先于环境，部分环境配置立即失败。Key 永远不是函数实参或配置字段，插件只把已解析 Provider 引用的凭据映射交给 Agent Manager。没有采用 `spotPatch(key, url)`，因为位置参数无法表达模型且会诱导把真实 Key 提交到 Git；没有默认猜测 lint/build，因为跨包管理器执行错误命令会制造虚假安全感。公共默认值 (见 doc-id:03-public-api-models)，Vite 生命周期 (见 doc-id:04-vite-plugin)，环境与认证边界 (见 doc-id:17-model-provider-credentials)。

### ADR-018：源码导航采用受控编辑器偏好与确认反馈

状态：Accepted。公共配置只允许 `auto | vscode | cursor`；`auto` 优先从启动 Vite 的受控集成环境识别 Cursor/VS Code，未知环境才由 `launch-editor` 后备探测，显式值只映射到固定 `code`/`cursor`。固定 CLI 只接收 `--goto` 与服务端授权后的绝对源码坐标，不使用 `--reuse-window`：后者会把文件强制交给最后活跃窗口，破坏多项目工作区归属；也不使用 `--new-window`，由编辑器按路径选择既有工作区。浏览器只提交已授权 source ID 与行列。服务端经过短暂启动确认后才返回实际采用的受控 editor 枚举，Runtime 校验响应并给出可见、双语状态；目标行和底部活动目标入口复用同一流程。源码导航是只读能力，与 Agent 编辑锁分离；Apply 后释放旧 DOM 引用但保留 source marker。没有采用任意 `editorCommand`，因为它扩大本地命令执行面；没有只依赖异步回调后立即 `200`，因为命令缺失会被误报为成功。公共值域 (见 doc-id:03-public-api-models)，插件适配 (见 doc-id:04-vite-plugin)，协议安全 (见 doc-id:09-local-protocol-security)，交互反馈 (见 doc-id:10-ui-diagnostics)。

### ADR-019：脏工作区采用显式同意的隔离快照，只应用和撤销 Agent 增量

状态：Accepted，取代 ADR-011 中“脏工作区一律拒绝”的限制，不改变 review 默认、安全工具或冲突拒绝。协议默认仍为 `require-clean`；健康检查发现 staged、unstaged 或有界普通 untracked 文件时返回 `consent-required`，只有用户对本次任务显式同意才使用 `include-local-changes`。宿主从源 HEAD 创建 detached worktree，把 tracked working-tree Diff 与有界 untracked 内容复制进去并复验，在隔离 worktree 内创建临时基线 commit；该 commit 不进入业务仓库分支，也不改变业务 index。Agent Diff 只相对该临时基线生成。Apply/Revert 复验源 HEAD、Git 操作状态以及 Agent 触及路径的 SHA-256；无关文件并发变化允许且保留，触及路径变化拒绝。Revert 逆向应用同一 Agent Diff并复验本地基线，因此不会撤销用户在任务前已有的改动。没有使用自动 stash/reset/业务仓库临时 commit，也没有整体恢复工作区，因为这些方案会改变 index 或误删用户内容。执行细节 (见 doc-id:16-ai-agent-execution)，协议与错误码 (见 doc-id:09-local-protocol-security)，验收 (见 doc-id:12-testing-acceptance)。

### ADR-020：原生可定制选择器渐进增强；核心 Runtime 预算调整为 38 KiB

状态：Accepted，选择器部分延续 ADR-004；包体数值取代 ADR-016 中“不提高 35 KiB 预算”的历史结论，Runtime/React Adapter 分包边界不变。Provider/Model 保留原生 `<select>`；支持 customizable select 的 Chromium 使用 `appearance: base-select`、`::picker(select)` 与 Popover 状态实现字段下方、可动画、深色且可访问的 picker，不支持的浏览器保留 `color-scheme: dark` 原生降级，不建立第二套 JavaScript 下拉状态机。工作区健康、显式本地修改同意和精确安全诊断使核心 Runtime 的 Linux Node 22 level-9 gzip 增至 38,713 bytes（约 37.81 KiB）；这些是防止覆盖用户代码的必要功能，不是装饰性体积。预算调整为严格 `< 38 KiB`，仍排除 React Adapter，并继续禁止把 provider、Git、parser 或服务端校验打入浏览器。后续增加功能必须在该门禁内优化或另立 ADR，不能无记录上调。UI 行为 (见 doc-id:10-ui-diagnostics)，包体验收 (见 doc-id:12-testing-acceptance)。

### ADR-021：Provider 工具 ID 按模型轮次作用域执行，原始 ID 只用于协议关联

状态：Accepted。OpenAI-compatible 中转站可能在不同 assistant turn 生成相同 `toolCallId`；原始 ID 的必要职责是关联当前 assistant tool call 与紧随其后的 tool result，不作为整个 Agent Job 的永久全局身份。SpotPatch 为每次模型响应生成从 1 开始的内部 `turn`，执行器缓存和 Runtime 活动以 `turn + toolCallId` 为键：同一轮相同逻辑调用的重放返回缓存结果，同轮相同 ID 但名称或参数冲突时 fail-closed，后续轮次相同原始 ID 则独立校验和执行。Job 工具事件升级为 schema v2，并显式携带 `turn`；旧 Runtime 必须通过正常依赖升级与 Vite 重启切换，不能猜测缺失轮次。Responses 流中同一逻辑 item 在增量与 completed 事件重复出现可以确定性归一，不得重复产生副作用。工具参数契约错误与同轮 ID 冲突使用独立错误码，旧通用码只为兼容保留；其中已经解析为对象的字段契约错误可以在确认零副作用后返回一次有界重试。`read_file` 路径拒绝同样可以作为统一、脱敏、零副作用结果交还模型，使其从枚举或搜索结果选择其他允许路径；该恢复不区分缺失与受保护路径，不回显原路径，也不适用于任何写工具。畸形 JSON、写路径拒绝和 ID 冲突不能重试。没有采用全局放行重复 ID，因为那会复用错误结果；也没有继续要求全 Job 唯一，因为该要求超出本地安全所需并拒绝合法中转实现。执行语义 (见 doc-id:16-ai-agent-execution)，协议与错误码 (见 doc-id:09-local-protocol-security)，provider 归一化 (见 doc-id:17-model-provider-credentials)，UI 活动 (见 doc-id:10-ui-diagnostics)。

本决策没有提高 ADR-020 的包体预算；Node 22.22.0 对发布核心 Runtime 的 level-9 gzip 实测为 38,708 bytes，严格小于 38 KiB，剩余 204 bytes。

### ADR-022：同一 Monorepo 按框架提供单一入口

状态：Accepted（架构与公共预览实现）。SpotPatch 不为 Next.js 创建第二个仓库；现有 Monorepo 已提供 0.x 公共预览入口 `@spotpatch/next`。ADR-007 的“一个用户入口”解释为“每个宿主框架只需一个入口包”，不是让 Next 项目安装 Vite 适配器。框架入口互为平级依赖方，不得相互依赖；用户选择与项目框架匹配的一个包 (见 doc-id:next-02-package-architecture)。

### ADR-023：Next 接入使用配置包装器、开发 CLI 与 instrumentation-client

状态：Accepted（公共预览实现），正式支持仍受阻断式 POC/N4 约束。`withSpotPatch` 组合 `next.config`，`spotpatch-next dev` 拥有 Sidecar 与 Next 子进程，并通过一次性初始化把同步 hook 入口接入官方 `instrumentation-client`。不采用 Custom Server、Deployment Adapter、强制 Babel 或私有 Next Compiler 插件：前三者分别会改变宿主部署/优化边界，后者缺少稳定公共契约 (见 doc-id:next-03-integration-lifecycle)。

### ADR-024：先抽取框架无关编译与开发服务内核

状态：Accepted（已实现）。通用 source transform 已抽入 `@spotpatch/compiler`，Node 选项解析、协议、Source Registry、编辑器与 Agent 装配已抽入 `@spotpatch/dev-server`。Vite/Next 分别导出 Adapter 专用 options 类型，组合公共子类型但不相互导入；应用根、Git 根和源码授权根必须分离。公共协议和数据模型继续保持单一事实来源，Vite 零回归仍是强制门禁；禁止复制 Vite 私有实现或从发布包深层导入 (见 doc-id:next-02-package-architecture)。

### ADR-025：Next 的 Turbopack 与 webpack 共用 Loader 契约

状态：Accepted（锁定范围公共预览），正式支持仍受完整 Loader/N4 矩阵约束。Next 16 默认 Turbopack，而 Next 15 与显式 `--webpack` 仍是候选支持面；同一薄 Loader 调用公共 compiler。2026-08-09 的锁定版本 macOS 与 Ubuntu/Node 22 POC 已证明无 `as` 的 TSX 输出链在 Next 15.3.9/16.3.0 可运行，并覆盖生成的 500 模块、并发冷请求和暖 cache 重启；其余 N1/N4 证据仍未完成。仅支持 webpack 的结果不得成为 Next 正式支持声明，Loader 选项不得携带 secret 或不可序列化对象 (见 doc-id:next-04-transform-source)。

### ADR-026：本地能力由 loopback Sidecar 承载并分离信任通道

状态：Proposed，受 rewrite 与多进程 POC 约束。Next 没有稳定的开发 middleware 插件点，本地协议由 CLI 所属 Sidecar 承载，经 `beforeFiles` external rewrite 提供同源浏览器访问；浏览器 session 与 Loader 内部注册使用不同的高熵凭据和授权规则。Sidecar 只改变承载方式，不重定义公共 endpoint、错误码或文件安全 (见 doc-id:next-05-sidecar-protocol)、(见 doc-id:next-07-security-production)。

### ADR-027：RSC 精确定位以 host marker 为主，Fiber 只提供可降级语义

状态：Accepted（架构与公共预览实现）。Server Component 可以在服务端产出带 marker 的 host 元素，但不保证浏览器 Fiber 暴露完整 Server Component 身份；因此精确文件行列继续来自构建期 marker，组件名与栈只在真实可用时展示，不从相邻节点或文件名伪造。React 18/19 均不得为了 SpotPatch 强制改变宿主 JSX runtime (见 doc-id:next-06-rsc-runtime)。

### ADR-028：Next 支持声明由证据门禁驱动

状态：Accepted。`@spotpatch/next` 的正式支持声明必须晚于 Turbopack/webpack、App/Pages Router、RSC、Sidecar、安全、生产零残留、Vite 零回归和 Registry 冷安装全部验收。关键 POC 未通过时应调整架构或收窄兼容范围，不能用 warning 把核心定位或安全失败包装成“已支持” (见 doc-id:next-08-testing-delivery)。

### ADR-029：Next 配置由真实 Next 求值并通过私有 IPC 配置父 CLI

状态：Proposed，受多进程 POC 约束。父 CLI 不重复 import/执行 `next.config`，不复制 Next `.env*` 加载规则；本地 Next child 在开发 phase 真实求值对象、同步或异步配置后，`withSpotPatch` 通过版本化、带启动 nonce、严格 schema 和超时的父子 IPC 发送一次规范化配置。owner 完成校验和 Sidecar 初始化后 ack；完全相同的重复消息幂等，不同配置重复消息失败。Provider Key 可以在可信服务端配置求值期间被解析并经私有 IPC交给 owner，但不得进入 NextConfig 返回值、Loader options、日志、cache 或浏览器。直接 `next dev` 无 IPC 时清晰失败，不在配置副作用中启动服务 (见 doc-id:next-03-integration-lifecycle)、(见 doc-id:next-05-sidecar-protocol)。

### ADR-030：Next 首版开发拓扑强制双 loopback，不支持 LAN

状态：Accepted（首个公共预览已实现）。external rewrite 会把访问 Next dev server 的客户端代理到 loopback Sidecar，所以 Sidecar 自身监听 loopback 不能隔离局域网。CLI 必须在用户未指定时显式把 Next child 绑定 loopback，并拒绝非 loopback `-H/--hostname`、等价 IPv4/IPv6地址与 `allowLan: true`；Sidecar继续只绑定 loopback。远程容器、Codespaces和 LAN使用需要新的认证、origin、编辑器和代理信任模型，不能继承 Vite 配置推断安全 (见 doc-id:next-07-security-production)。

### ADR-031：源码注册以启动 epoch 隔离 cache，注册成功后才注入 marker

状态：Proposed，受 Loader/cache POC 约束。随机 fileId 只在当前 Session 有效，而 Turbopack/webpack 可能持久化转换结果；每次 CLI启动生成非敏感 `registryEpoch`，作为 Loader cache identity 和 worker LRU key 的组成部分。Loader必须先让当前 epoch 的 Registry成功登记路径，再调用 compiler 注入 marker；超时、崩溃或 epoch不匹配返回完全未注入的原模块。Sidecar崩溃终止 Next，禁止原地创建空 Registry继续接受旧 marker。epoch只用于失效缓存，不是认证 secret (见 doc-id:next-04-transform-source)、(见 doc-id:next-05-sidecar-protocol)。

### ADR-032：跨页面选择使用有界会话草稿；核心 Runtime 预算调整为 40 KiB

状态：Accepted，取代 ADR-020 的 38 KiB 数值门禁，不改变 Runtime/React Adapter 分包边界。已完成采集的目标按同源、同标签页和当前开发服务 `sessionId` 写入 `sessionStorage`；鉴权 token 不进入键或值，开发服务重启后旧草稿自动隔离。关闭工作台只记录隐藏状态，显式“Start over”或移除全部目标才删除草稿；SPA 卸载仅释放 Element/Observer 引用，保留已经清洗的 DOM、样式、源码和逐目标说明。每个目标携带自己的页面上下文，跨页面 Prompt 和 Agent 请求不得把所有目标误归到最后页面。恢复入口对 JSON 大小、目标数量和运行时所需结构做浏览器侧有界校验，服务端继续执行完整协议与源码授权校验；没有使用长期 `localStorage`、鉴权 token 派生键、宿主路由 API 或持久化 DOM/Fiber 引用。该必要状态模型使核心 Runtime 的 level-9 gzip 超过旧 38 KiB 门禁，因此预算调整为严格 `< 40 KiB`，仍禁止把 Zod、provider、Git、parser 或 React Adapter 打入核心浏览器产物。生命周期 (见 doc-id:05-runtime-lifecycle)，UI 行为 (见 doc-id:10-ui-diagnostics)，包体验收 (见 doc-id:12-testing-acceptance)。

### ADR-033：显式能力探测改为可选诊断，真实任务以内联工具往返证明能力

状态：Accepted。首次运行不再固定先执行无源码 probe 的两个远程模型往返；“检查运行环境”继续提供显式、可缓存且不含项目数据的诊断。用户完成 provider 数据传输同意后，真实 Job 直接在 detached worktree 中启动，首轮必须产生合法工具调用并成功续接工具结果；只返回文本、无法续接或协议畸形均失败并清理 worktree，不能形成可 Apply 结果。该变化删除纯延迟，不把模型能力名称当证据，也不削弱路径、检查、Diff、review/auto 与基线门禁 (见 doc-id:17-model-provider-credentials)、(见 doc-id:16-ai-agent-execution)。

### ADR-034：项目规范由就近证据驱动；性能缓存按变更版本失效

状态：Accepted。Agent 首次输入从目标目录向根收集有界、脱敏的格式/语言配置、包元数据与同目录实现样例。review/auto 只把 check ID/显示名/required 状态交给模型，不发送命令参数；由宿主实际执行且此后没有写入的 `run_check` 可以直接成为最终 required check 结果，缺失或过期项仍由宿主补跑。trusted-auto 不下发检查定义或 `run_check`，而是优先使用 SpotPatch 已提供的精确路径并在成功写入后直接结束。所有模式的只读工具都可同轮并发，文件目录和内容在当前 worktree 版本内缓存，最终统一复验 Diff。没有采用全仓源码预载、跨 Job 缓存、模型自报检查成功或永不过期索引，因为这些方案分别扩大传输、造成陈旧结果或削弱边界可信度 (见 doc-id:08-code-prompt)、(见 doc-id:16-ai-agent-execution)。

### ADR-035：外部 Agent 使用显式 Handoff，MCP/CLI 为公共主链路

状态：Accepted（架构）；工作区公共实现已进入 `local-validation`，但支持声明仍受 (见 doc-id:external-agent-08-testing-delivery) 的 EA-1B 与后续发布 Gate 约束，不表示任何真实客户端或跨平台兼容已经交付。

决策：SpotPatch 选择组件后不自动发送。用户完成逐目标说明并明确点击发送后，Node dev-server/Sidecar 复用现有 Source Registry 和 `SpotAnnotation` v3 授权规则，重新读取当前源码，在内存中生成有 TTL 的不可变 Handoff revision。Claude Code、Cursor、Codex 和其他本地 Agent 通过一个只读 MCP stdio Connector 的 `list/get/wait/ack` 工具读取；CLI JSON 复用同一 discovery/Broker client 作为后备。Connector 通过用户私有发现描述符连接专用 `127.0.0.1` Broker，描述符只含连接元数据和独立 bridge token，不写 annotation、DOM、instruction 或源码。浏览器 token 与 bridge token 分域，Vite/Next 只负责装配共享 dev-server 实现。

标准 MCP 可以可靠提供 Agent 查询和进行中的有界等待，但不能保证在没有工具调用时向所有宿主的活跃对话主动注入内容。因此 Generic MCP/CLI 只承诺 `published`、`picked-up`、`expired` 等有证据状态，不宣传通用“点击即推送到对话”。Claude Channels 与 Codex App Server 是 ADR-036 管理的独立主动 adapter；它们只消费同一授权 Handoff，不能改变公共 Schema 或绕过 Node 授权。Cursor 和其他没有已验证入站 API 的宿主保持 Inbox-only。

Generic MCP/CLI Connector 不提供文件写入、Shell、Git、模型调用或 Apply/Revert。attached adapter 仅在用户显式启动后通过宿主入站协议触发任务，并且只上报有证据的有界生命周期，不会直接绕过宿主写项目。Generic/attached 使用宿主自身的 workspace trust、sandbox、审批和数据政策，SpotPatch 不把内建 Agent 的 worktree/checks/Diff 保证延伸给它们。ADR-037 另行接受的 Codex managed 是唯一例外：它通过 `@spotpatch/agent` 窄端口复用隔离和回写原语，不改变 Generic/attached 权限。

被拒替代方案：

- 浏览器直接 spawn 厂商 CLI：浏览器无权安全决定命令、参数、cwd、会话和审批；多厂商生命周期会污染 Runtime。
- 每个厂商一套交接 JSON/endpoint：复制模型、授权和错误语义，无法维持 Vite/Next 一致性。
- 把完整快照写临时文件供 Agent 读取：增加源码/DOM 的崩溃遗留和清理面；内存 Store + 无正文发现文件更小。
- 仅用 MCP resource notification：host 行为不一致，无法作为主动交付保证。
- 首版公开 Streamable HTTP/公网 MCP：stdio 已覆盖目标本地宿主，远程服务会引入新的身份、TLS、隧道和源码外发威胁。
- 用命令行 `--client claude|cursor|codex` 作为安全 audience：标准 MCP 不提供可验证的对话身份，标签可伪造；首版诚实采用项目 Inbox 语义。

### ADR-036：主动派发使用单活 Event Pump 与宿主能力适配器

状态：Accepted（架构）。实现状态只由 (见 doc-id:external-agent-00-index) 维护；Claude Channels 仍是 Research Preview，Codex App Server command 仍是 experimental，Claude/Codex 的真实“双次点击 → 执行 → idle → 再执行”证据未通过前不得标稳定支持。

决策：保留 ADR-035 的 Handoff Store、loopback Broker、MCP/CLI Inbox 作为事实源和跨宿主上下文基线；新增一个运行在 `@spotpatch/bridge` 的非模型 Event Pump。Adapter 真正 ready 后，Pump 对目标 dev Session 原子取得唯一短 lease 与 `baselineCursor`，不允许 claim 后再读 current，也不重放旧写任务。同 kind + 同 `connectorInstanceId` 的 claim 重试返回原 lease/baseline 并刷新租期；instance ID 不是认证，所有生命周期写入仍验证高熵 lease token。之后 Pump 用现有有界 Broker wait/自动 pickup receipt 接收新 revision，交给一个窄 `AgentAdapter`，按结构化证据上报 lifecycle，并在明确 terminal 后重新等待。厂商代码不进入 Runtime、dev-server、Vite/Next 或 HandoffSnapshot。

Claude Code 适配使用运行中会话显式启用的 Channel MCP capability 与 `notifications/claude/channel`，事件只携带 session/revision/cursor 引用。Channel transport 既没有 notification ACK，也没有 completion ACK，所以通知成功最高只表示 `dispatched`；exact-cursor 取件 tool 和显式 `spotpatch_report_handoff_result` 分别是 working/terminal 证据，未调用结果 tool 时不得猜测完成。当前锁定组合还要求宿主 Claude 进程使用 `MCP_PROTOCOL_NEGOTIATION=legacy`。首版不启用 permission relay，不绕过 Claude 权限，未上报结束时有界转为 `delivery-unknown`。

Codex 适配由用户在精确项目根用一条 `connect codex --allow-workspace-write` 显式运行 SpotPatch Connector；不需要 nvm 或预先 setup，多 Session 使用 opaque `--session`。Connector 不读取或修改项目 `.codex/config.toml`，而从受信框架 adapter 生成固定 SpotPatch MCP command/args，作为 thread 级配置注入。持久 Codex Inbox 与主动 inline 入口共用固定 `XDG_RUNTIME_DIR` / `TMPDIR` / `TMP` / `TEMP` 名称白名单，只由 Codex 转发现有值，不写入值、不传递完整环境、不允许 Browser/Handoff 扩展。随后从可信终端 PATH 解析、realpath 和验证绝对 `codex-cli 0.149.0`，以固定 argv `app-server`、`shell: false` 启动，拥有一个项目专用 thread。主动 MCP command 内部追加精确 `--session`，并通过 `enabled_tools = ["spotpatch_list_sessions"]` 从模型工具面移除 full-context get/wait/ack。初始化后先用 `mcpServerStatus/list` 验证只注册该 tool，出现额外 tool 即 fail closed；再由 `mcpServer/tool/call(spotpatch_list_sessions)` 验证绑定后只返回精确选定 Session，成功后才 claim。该状态查询会受用户其他已启用 MCP 的初始化耗时影响，因此 JSON-RPC 默认有界超时为 30 秒且终端预先披露其他 MCP 可能启动。每个空闲 Handoff 使用 `turn/start`；只有全部目标具备可执行相对源码位置时，输入才携带相对路径、行列、仅标签名的元素标识和逐目标 instruction，不携带 DOM selector/CSS/源码摘录，缺少位置时在厂商写入前报告 failed。这为主动 Codex 整体序列化大型 tool result 的已知失败路径建立了协议级阻断和自动化证据；修复后已在记录的 macOS/Next.js/Codex 0.149.0 环境人工完成连续两 revision，但仍缺少跨平台和可重复真实宿主自动化。成功 response、匹配 `turn/started` 与 `turn/completed.params.turn.status` 分别对应 dispatched、working 与协议 terminal；completed 不证明修改成功。首版不 `turn/steer`、不接管未知 Codex UI thread、不持久化厂商 ID。写模式必须在终端显式启用，cwd 固定为 canonical root，sandbox 为 workspace-write、network false、approval 固定 never；已知反向 request 按 Schema decline/cancel，未知 method 才返回协议错误。Codex 仍可按用户既有配置启动其他 MCP server；Connector 只保证同名 SpotPatch thread 配置和 exact-session Session-list 就绪验证。开发 Session 结束/重启后旧 exact-session Connector 停止并提示重跑，不无限退避或静默重绑定。POSIX 上以独立进程组清理 App Server 及子孙；Windows 进程树清理仍为 `not-tested`。App Server 可能持久化 project trust 的外部副作用必须在终端披露和 POC 中记录。

主动 Codex 的多目标摘要还要求“投影后源码位置 + 安全标签”在同一请求内唯一；原始 selector、id、`data-testid` 和 HTML 属性不能为了消歧进入 turn。投影缺失或碰撞时在 `turn/start` 前报告 failed，让用户重新选择可定位目标，而不是让模型猜测。

同一 dev Session 只允许一个 SpotPatch 管理的主动 lease、一个未终止 dispatch；相同 root 的其他 Session 与 Generic MCP 消费者不受该内存锁排他。Browser 每次点击生成随机 requestId；同 ID/同请求幂等，同 ID/不同请求拒绝，publish 响应原子返回实际 Inbox/active mode。busy 时不创建第二个 revision，不做 FIFO/latest-wins/自动合并/主动广播。已可能送达但确认丢失时进入 `delivery-unknown`，停止并释放 writer、保持 hazard blocked，只有用户明确核对工作区后才能解除且不重发旧任务。没有正式入站 event/turn API 的 Cursor/其他 MCP Agent 保持 Inbox-only，不提供虚假的 Generic Push Adapter。

被拒替代方案：

- 让模型永久循环 `wait_for_handoff`：占用模型 turn，工具返回后不会天然重新订阅，cursor 恢复还泄漏到用户对话。
- Stop hook 阻止 Claude 结束并继续等待：依赖 continuation 保护上限，浪费推理生命周期，不是事件通道。
- 通用 `command + args` adapter：把受限交接扩大成浏览器可间接驱动的任意本地命令执行器。
- busy 时自动 `turn/steer`、队列或 latest-wins：会把独立用户动作隐式合并、让源码上下文陈旧，或丢弃用户意图。
- 多 adapter 同时消费 Store waiter：Store 的广播读取语义适合 Inbox，不适合自动 writer。

详细状态、协议、安全、交互和 Gate 见 (见 doc-id:external-agent-09-active-dispatch-adapters)、(见 doc-id:external-agent-04-handoff-protocol)、(见 doc-id:external-agent-06-security)、(见 doc-id:external-agent-07-ux-performance-observability)、(见 doc-id:external-agent-08-testing-delivery)。

### ADR-037：Codex 托管模式由 dev 生命周期持有，并在独立快照验证后回写

状态：Accepted（规范目标；工作区实现为 `local-validation`）。实现与发布状态只由 (见 doc-id:external-agent-00-index) 维护，不以本 ADR 代替真实宿主或跨平台证据。

决策：Codex 新的默认主动路径由 `pnpm dev` 内唯一 `ExternalAgentSupervisor` 持有，不再要求用户每次运行第二个 `connect codex` 进程。页面只能选择服务端枚举的 adapter/profile、请求诊断和撤销；首次 `managed-apply-v1` 必须由当前 dev 终端的一次性 challenge 明确确认，无 TTY 时保持 Inbox。grant 位于用户私有 OS 配置目录，只保存 project key、adapter、固定 profile 和版本事实，不保存源码、绝对路径、凭证或厂商会话。

每个 revision 在系统临时目录创建独立 Git 快照仓库，不创建指向业务仓库 Git 元数据的 linked worktree，不 stash/reset/改 index。managed profile 不复用 ADR-019 的 `include-local-changes`：本次 Source Registry 授权的目标路径必须是 HEAD 中已跟踪且 staged/unstaged 均无修改的普通文件；其他本地改动按 ADR-039 从快照排除并保留，不再造成全仓误阻断。Agent 的 writable roots 只包含快照工作区；独立快照 Git 元数据位于工作区外的同任务临时目录并只作为 restricted read root，网络关闭，approval 固定 never。用户其他 MCP、hooks、plugins 若不能由锁定版本证明隔离，managed preflight 必须失败并降级 Inbox。`process/*`、`thread/shellCommand`、experimental API、danger-full-access、任意 shell 和 Browser 自定义 command/cwd/model/sandbox 都不进入端口。

SpotPatch 只执行可信项目配置中显式声明的 required checks，不按 package scripts 名称猜测验证命令。`not-configured`、`unavailable` 或 `failed` 一律进入 `review-required`，业务仓库不变；只有全部 required checks `passed`，allowed paths、change-set、基线哈希和规模策略均通过后，才可执行冲突安全 apply。apply 使用预检、逐文件哈希、结果复验和匹配哈希补偿回滚，不宣称进程崩溃意义上的跨文件事务原子性。

连接、投递、厂商执行和 managed pipeline 使用四条正交状态轴。Claude transport write 不等于 accepted；Codex `turn/completed` 不等于工程完成；只有 apply 后一致性证明可以产生 managed `completed`。账户 readiness 不从 `account: null` 单字段猜测；请求模型与 `model/rerouted` 后的实际模型分开记录。每 revision 使用新 thread，终态删除；崩溃时只在用户私有 cleanup journal 留 opaque thread id 并于下次启动清理。

ADR-037 只取代 ADR-036 中 Codex “独立终端 Connector、业务仓库直接 workspace-write、持久单 thread、继承其他 MCP”的目标形态。ADR-035 的 Generic Inbox、ADR-036 的 Broker/Registry/Event Pump 和 Claude attached adapter 继续有效。完整实施契约、固定降级和 Gate 见 (见 doc-id:external-agent-10-convergence)。

### ADR-038：外部 Agent 受管控制保留独立 dev-only chunk，预算为 16 KiB gzip

状态：Accepted。页面连接管理新增严格有界协议解析、双语连接/授权/模型/四轴状态、取消与撤销操作，以及 diff、checks、阶段耗时结果；这些能力是 ADR-037 的安全控制面和可观测证据，不能删除或移入核心 Runtime。Vite/Next 继续只在 `externalAgent` 启用时加载既有独立入口，核心 Runtime、React adapter、data-flow panel 和生产构建预算均不改变。macOS Node 26 level-9 实测该独立产物为 `14,366 bytes gzip`，门禁设为严格 `< 16 KiB`，只保留跨平台 zlib 的窄余量。该 chunk 仍禁止 MCP SDK、Zod、Node-only 依赖、凭证和厂商原始协议；后续增长必须先优化或新增 ADR，不能静默提高门禁。唯一预算位置见 (见 doc-id:external-agent-07-ux-performance-observability)，发布门禁见 (见 doc-id:external-agent-08-testing-delivery)。

### ADR-039：Codex 托管快照只要求授权目标路径干净

状态：Accepted，收窄 ADR-037 的全仓 `require-clean` 门禁，不改变独立快照、allowed paths、哈希冲突检查或 ADR-019 的本地修改纳入语义。

决策：managed runner 在拿到 Node 重新授权的目标路径后才创建快照。每个目标必须位于当前项目根内、已由 HEAD 跟踪、仍存在且相对 HEAD 没有 staged/unstaged 修改；任何一个目标不满足时在启动 Codex thread 前返回 snapshot failure。仓库中与目标无关的 staged、unstaged 和普通 untracked 内容不复制到快照、不进入 Prompt/工程规范收集、不授予 Agent 读取或写入，同时也不阻断任务。快照仍只从可信 HEAD 独立 clone，apply 前复验源 HEAD、Git 操作状态以及 Agent 实际触及路径的基线哈希；因此无关改动原样保留，目标并发变化仍拒绝覆盖。

该策略不等价于 `include-local-changes`，不需要把长期 managed grant 扩大为“发送全部未提交代码”的同意。若未来需要让 Agent 基于目标文件本身的未提交内容工作，仍必须新增逐任务、可见的数据纳入确认和独立临时基线 ADR；不得静默复制、stash、reset、改 index 或 commit 业务仓库。Git 冲突、merge/rebase/cherry-pick/revert 进行中、HEAD 变化、目标未跟踪/删除/符号链接以及路径归一化失败继续 fail closed。此收窄解决 `init` 产生的无关未提交集成文件让首次 managed 任务必然失败的问题，同时不扩大模型可见数据和写入范围。

ADR-001/002/017/018 的实现位置 (见 doc-id:04-vite-plugin)，ADR-004/015/018/020/021/032/033 的界面位置 (见 doc-id:10-ui-diagnostics)，ADR-007/008/016/020/022/024/034 的总体包结构 (见 doc-id:02-architecture-stack)、(见 doc-id:next-02-package-architecture)，ADR-013/014/019/021/032–034 的交互和执行位置 (见 doc-id:05-runtime-lifecycle)、(见 doc-id:16-ai-agent-execution)，ADR-023/025–031 的 Next.js 专项细节只在 Next.js 专题规范维护 (见 doc-id:next-00-index)，ADR-035–039 的目标契约只在外部 Agent 专题维护 (见 doc-id:external-agent-00-index)。

## 最终工程判断

SpotPatch v1 的最小正确实现不是一个高亮框，而是以下四条链路同时成立：

```text
元素 → 准确的 JSX 位置
元素 → 合理的 React 业务组件
元素 → 经过清洗和预算控制的 DOM/CSS/代码
上下文 → 可预览、可复制、可直接执行的 AI Prompt
```

SpotPatch v1.1 AI 扩展只有在以下附加链路同时成立时才算“可以改代码”：

```text
可信 Provider 配置 → 显式探测或真实任务内联证明 → 结构化工具调用
不可信模型输出 → 本地工具授权 → 隔离 worktree
隔离变更 → 安全校验 → required checks → Diff 审阅
用户 Apply / 受限 auto → 基线复验 → 本地文件 → 可冲突检测的 Revert
```

外部 Agent 连接只有在对应链路成立时才算“完成上下文交接”，但这仍不等于代码已安全修改：

```text
显式发送 → Node 重新授权 → 内存 Handoff revision → 当前项目 Connector
  ├─ Generic Inbox / Claude active → loopback Broker → MCP get / 有界 wait → 结构化上下文
  └─ Codex active → 有界任务投影 → 专用 App Server turn
外部 Agent → 宿主自己的审批、编辑与检查
```

标准 MCP 只能让 SpotPatch 证明发布和取走，不能证明模型理解、修改或验证成功。外部执行不能继承内建 Agent 的 worktree/Apply/Revert 结论。

实现优先级必须始终是：

```text
准确性 > 安全性 > 降级清晰度 > 性能 > UI 精致度 > 功能数量
```

v1 成功的证据不是“页面上出现了工具栏”，而是在真实项目抽样中达到定位准确率、安全和生产零残留指标。v1.1 成功也不是“模型回复了代码”，而是 provider contract、工具授权、Git 隔离、checks、审阅、冲突和凭据泄漏门禁都有可重复证据。多标注、Issue 集成和操作录制仍需后续独立决策。

量化验收口径见测试与验收 (见 doc-id:12-testing-acceptance)，安全验收见安全规范 (见 doc-id:09-local-protocol-security)，产品范围见产品定义 (见 doc-id:01-product-boundary)。
