## 用户业务项目只读结果

对 `shengsuanyun-newmodel/src` 的 **66 个 `.astro` 模板**执行了可重复探针：原文解析、注入、编译；移除本次新增 marker 后与原文逐字一致。没有改动业务项目源码、依赖、配置或本地环境文件，也没有启动其 BFF/鉴权服务。

复现入口在 [包 README](../../../packages/astro/README.md#maintainer-verification)，通过 `SPOTPATCH_ASTRO_SOURCE_DIR` 传递目录；仓库代码没有硬编码用户磁盘路径。此结果说明模板语法可处理，**不等于该业务项目完整运行环境已完成联调**。

## 调研中解决的冲突

- 旧 Astro compiler 的 AST 位置与复杂属性解析不能满足精确插入：采用官方 compiler-rs 的 UTF-16 位置并校验源文本，未保留旧 scanner/转换实现。
- HTML spread 的重复属性采用 first-wins，和 JSX 相反：Astro 标记置于 tag name 后；独立真实浏览器断言验证。
- Astro 编译器自身是 pre 插件：增加 transform hook 的 `order: pre`，避免处理已编译 JS。
- 源码 API 新语言需要贯穿服务端、共享 schema、Runtime 校验与 Prompt：统一支持 astro，未只修改扩展名白名单。
- CLI mode 不在初始 Astro 配置中可靠表达：凭据延后到 Vite configResolved，采用最终 mode/envDir。
- Node 22.12 测试首次被系统 pnpm 11 的 Node 22.13 下限阻止：改用仓库声明的 pnpm 10.34.5 后 6 项浏览器测试通过；不是修改插件 engine 来掩盖工具链冲突。
- 同时运行全仓测试、包构建和 Next 编译探针时，一轮已有进程测试出现 4 项失败及取消错误；结束其他构建后，未修改断言或超时，原样重跑 `pnpm test:unit` 得到 908 passed / 5 skipped。发布验证应避免让这些进程时序测试与大型编译任务争抢资源；这不是对所有时序稳定性的证明。
- lockfile 增量包含三套 Astro fixture、compiler-rs 原生/可选 WASM 依赖及相关 peer graph；根目录的 @emnapi/core/runtime 开发依赖用于满足严格 peer 安装检查，未关闭 strict-peer-dependencies，也未升级既有框架的直接版本声明。

## 仍未覆盖、不得扩大声明

1. npm 发布及 registry 干净安装；当前仅提供本地源码链接流程，Changeset 已添加。
2. Windows/Linux 与其他 CPU 的 CI 运行结果：已新增三平台 Node 22 Astro job，但本次没有远程 CI 证据。
3. 用户项目的真实 BFF、反向代理、登录态与 programmatic launcher 全链路联调；SSR/server adapters、任意历史补丁版本及自定义 integration 顺序。
4. 完整浏览器 AI Review/Apply/Revert 操作链和真实 provider；当前证据是源码授权测试 + Agent 引擎真实写入/回滚测试，不能冒充浏览器 AI E2E。
5. 服务器重启与独立 `astro preview` HTTP 冒烟：已有正常启动/关闭、多次独立启动、ClientRouter/HMR 与非 dev 门禁/生产扫描，但不把它们扩大解释为所有重启和部署模式已验证。
6. island 内部精确定位、MDX、lit-html/动态 HTML、组件数据链路、外部 Agent、Ask、trustedFastMode：本版明确不支持或只能祖先降级，需要独立设计与验收。

新增适配器因此保持 source preview，不改变现有正式支持矩阵。所有后续发布动作应在这些边界基础上决定，而不是仅根据 peerDependency 范围宣布全面兼容。
