# 模型提供商与凭据配置

本文件是 AI provider profile、URL、认证凭据、模型选择、协议兼容、能力探测、流式传输和 provider 数据边界的唯一事实来源。本能力遵守默认关闭的产品边界 (见 doc-id:01-product-boundary)。本地工具、Git worktree、补丁、检查和 Apply/Revert 由 Agent 执行规范定义 (见 doc-id:16-ai-agent-execution)，公共配置类型、默认值和限制由公共 API 文档定义 (见 doc-id:03-public-api-models)，发送上下文的组合与预算由 Prompt 规范定义 (见 doc-id:08-code-prompt)，浏览器到 Vite Node 的本地协议由安全规范定义 (见 doc-id:09-local-protocol-security)。

## 核心判断

SpotPatch v1.1 不要求 Codex CLI。首个正式 provider 类型是 `openai-compatible`：用户通过约定式本地环境、简洁单 Provider API 或完整 Provider API 向 Vite Node 指定 Base URL、Key 所在环境变量、认证类型和模型名称；SpotPatch 自己实现 Agent 工具循环和本地执行。

URL、Key 和模型名只能建立推理连接，不能单独证明模型具备 Agent 能力。只有 provider 对指定协议、流式事件和结构化工具调用的实际探测全部通过，UI 才能启用“运行 AI 修改”。

## Provider profile

每个 profile 由公共配置中的稳定 ID 标识。profile 的字段与默认值只在公共 API 中声明 (见 doc-id:03-public-api-models)，本节规定解析行为：

- `type`：v1.1 只接受 `openai-compatible`。
- `label`：可以安全展示给用户的 provider 名称，不包含 URL、账号或 Key。
- `protocol`：完整配置显式选择 `responses` 或 `chat-completions`；简洁/约定式配置默认 `chat-completions`，两者都不得根据错误静默切换。
- `authentication`：只允许 `bearer` 或 `x-api-key`；完整与简洁配置默认 `bearer`。
- `baseURL`：只在 Vite Node 端解析和使用。
- `apiKeyEnv`：保存环境变量名称，不保存 Key 值。
- `models`：以稳定 model profile ID 映射到显示名和 provider 模型名。
- `defaultModel`：必须引用同一 profile 中已登记的 model profile ID。

浏览器只接收 provider profile ID、model profile ID、显示名、能力状态和脱敏错误，不接收 Base URL、实际模型名、环境变量名、请求 header 或 Key。

## 支持协议

### Responses adapter

`responses` 是首选协议，必须支持：

- `POST /responses` 或 Base URL 规范化后等价的 v1 endpoint。
- `stream: true` 的 SSE 响应。
- function tool 定义、工具调用 ID、参数和工具结果回传。
- 多轮状态延续；可以使用 `previous_response_id`，也可以按协议重放完整必要状态。
- 最终完成、失败、不完整和取消状态的明确事件。

provider 支持原生 `apply_patch` 时可以在后续版本增加优化 adapter，但 v1.1 不依赖该内建工具；为保持中转站兼容性，代码修改统一通过 SpotPatch 声明的 function tools 进行 (见 doc-id:16-ai-agent-execution)。

### Chat Completions adapter

`chat-completions` 是兼容回退协议，必须支持：

- `POST /chat/completions`。
- `stream: true` 的 SSE 响应，或经能力探测确认的非流式工具调用。
- `tools`、`tool_choice`、tool call ID、函数名和 JSON arguments。
- assistant tool call 与对应 tool result 的正确多轮关联。
- 明确的完成原因和错误响应。

Chat Completions adapter 必须把 provider 特有 chunk 转换为与 Responses adapter 相同的内部事件；Agent Engine 和 UI 不得分支处理 provider 原始格式。

### 不支持的兼容层

以下能力不足以启用自动修改：

- 只有 `/completions` 或纯文本聊天。
- 只能输出 Markdown 代码块或自然语言 patch。
- 工具调用没有稳定 ID，无法关联结果。
- 工具参数不能被可靠解析为 JSON 对象。
- 流事件缺失完成/错误边界，且非流式模式也无法稳定使用。
- 中转站把未知字段静默丢弃，导致工具或状态语义不成立。

能力不足时可以保留 Prompt 预览和复制，但禁止从模型文本中提取命令、路径或代码块后自动执行。

## Base URL 安全

Base URL 在 Vite 启动时校验，规则如下：

- 必须能被标准 `URL` 解析。
- 远程地址只允许 `https:`；`http:` 只允许语义明确的 loopback host。
- 禁止 URL username、password、query 和 hash。
- 标准化重复斜杠和尾部斜杠，endpoint 只由 adapter 追加一次。
- 请求使用 `redirect: "error"`；禁止带 Authorization 自动跟随重定向。
- 禁止通过浏览器请求动态覆盖 host、port、path 或 protocol。
- v1.1 不关闭 TLS 证书校验，不支持 `NODE_TLS_REJECT_UNAUTHORIZED=0` 等全局降级。

Base URL 是可信开发配置，不是模型输入。若未来支持多个 profile，UI 也只能提交已登记 ID，服务端必须重新解析真实 profile。

## 凭据

### v1.1 支持方式

v1.1 只接受环境变量引用，并支持两种固定认证类型：

```text
apiKeyEnv: "SPOTPATCH_AI_API_KEY"
```

`bearer` 写入 `Authorization: Bearer <key>`；`x-api-key` 写入同名请求头。两者互斥，同一次请求不得同时发送。不得在公共配置类型中提供明文 `apiKey: string` 或任意 header map；`apiKeyEnv` 必须匹配大写环境变量名规则，且不得以 `VITE_` 开头。

Key 的处理要求：

- 在 Vite Node 端加载配置，并在每次 provider Job 开始前从隔离的凭据映射解析。
- 启用 AI 时缺失或空值使 Vite 启动失败，不发网络请求。
- 只按已解析的固定认证类型写入一个认证 Header；不开放浏览器自定义 header。
- 不注入 Runtime 配置、HTML、虚拟模块、source map 或 provider capability 响应。
- 不传递给 Agent 检查子进程和业务构建命令。
- 不进入异常 message、debug 日志、遥测、快照测试或 Git Diff。
- provider 响应、URL 和日志在展示前再次执行常见 Key 模式脱敏。

`.env.local` 或 shell 环境变量可以承载 Key；项目必须确保本地 env 文件被 Git 忽略。由于 `VITE_` 变量会进入浏览器构建，任何 AI Key 都禁止使用该前缀。

### 约定式本地环境

未显式提供 `ai` 时，SpotPatch 在 Vite `config` 阶段读取当前 mode 对应的 env 文件与启动进程环境。只有以下三项全部非空时才自动启用 AI：

```text
SPOTPATCH_AI_BASE_URL
SPOTPATCH_AI_MODEL
SPOTPATCH_AI_API_KEY
```

可选覆盖项为：

```text
SPOTPATCH_AI_PROTOCOL=chat-completions | responses
SPOTPATCH_AI_AUTHENTICATION=bearer | x-api-key
```

协议默认 `chat-completions`，认证默认 `bearer`。三个必要值均不存在时 AI 保持关闭；只出现其中一部分、协议无效或认证无效时必须 fail-fast，错误只列变量名或允许值，不包含 Key。显式 `ai: false` 优先于环境并完全关闭发现；显式简洁/完整 `ai` 对象优先于 URL、模型、协议和认证环境值，但其 `apiKeyEnv` 指向的真实 Key 仍可以由 `.env.local` 提供。

插件可以调用 Vite `loadEnv` 读取本地文件，但最终只保留已解析 Provider 所引用的凭据变量映射并交给 Agent Manager；不得把完整 env 对象、Key 或配置文件内容放入 Runtime、虚拟模块、`define`、`import.meta.env` 或检查子进程。该约定使普通接入保持 `spotPatch()`，同时不降低 Node-only Secret Resolver 边界。

Shadow DOM 不是凭据隔离边界。v1.1 UI 不提供粘贴或查看 Key 的输入框；如果未来增加一次性凭据输入，必须另行 ADR，并证明页面业务脚本无法窃取该值。

### 后续扩展

操作系统 Keychain、Secret Manager 回调和固定类型之外的自定义认证 header 不属于 v1.1。增加新凭据来源时必须保持同一不变量：Secret Resolver 只存在于 Node 端，返回值不可序列化到公共配置或本地协议。

## 模型选择

- 用户可以在可信配置中登记任意 provider 模型名；SpotPatch 不假定名称对应某个具体厂商或能力。
- UI 只显示 model profile ID 和 label，不能输入任意模型名。
- 服务端必须校验 model profile ID 属于当前 provider profile。
- `GET /models` 可以用于诊断，但模型出现在列表中不等于支持工具调用，不能替代能力探测。
- 模型切换只影响新 Job；运行中的 Job 固定使用创建时的模型快照。
- provider 未返回 token usage 时 UI 显示“usage unavailable”，不得估算成精确费用。
- provider 模型别名可能漂移；需要可复现行为时由用户配置固定快照名，并通过真实任务 eval 验证。

## 能力探测

### 触发与缓存

能力探测在用户点击“测试连接”、首次运行或 profile/model 变化后执行。结果只缓存于当前 Vite 会话内存，并与 provider profile ID、model profile ID、protocol、authentication 和 Base URL 配置摘要绑定；Vite 重启后重新探测。

探测不得发送项目源码、DOM、CSS、用户问题、文件路径或工作区元数据。最小探针只要求模型调用一个无副作用的 `spotpatch_capability_probe` function，并校验一个固定短参数。

### 探测步骤

1. 解析 profile、URL、Key 和模型 allowlist。
2. 发起最小认证请求，区分认证、模型不存在、限流和协议错误。
3. 强制一次 function tool call，校验名称、call ID 和 JSON arguments。
4. 返回固定 tool result，验证模型能够继续并正常完成。
5. 在配置要求流式时验证 SSE 事件边界、顺序和终止状态。
6. 记录脱敏 capability 结果，不记录原始响应正文。

只有以下能力同时成立才标记 `agent-ready`：

- `authenticated`
- `model-available`
- `tool-calling`
- `tool-result-continuation`
- `streaming`（配置要求时）

探测失败必须返回本地协议定义的稳定错误码 (见 doc-id:09-local-protocol-security)。不得捕获一个错误后自动改用另一个协议，因为这会隐藏中转站实际契约并产生不同的计费或状态语义。

## 传输与事件校验

- 外部 provider 使用 Node `fetch` 和 `AbortController`；不把 provider 请求从浏览器直连出去。
- 所有 JSON、SSE event、tool arguments 和错误 body 都从 `unknown` 开始做运行时 Schema 校验。
- SSE parser 必须支持 chunk 任意切分、多个 event 同 chunk、UTF-8 多字节边界、空行终止和流中断。
- 设置连接、首字节、总 Job 和空闲超时；具体限制值由公共配置定义 (见 doc-id:03-public-api-models)。
- provider 响应正文、单事件和累计流量均设置上限，超限立即取消。
- 对 401/403 不重试；429 和明确 5xx 可以在尚未执行本地副作用时按有界退避重试。
- 工具调用开始后发生网络重试，必须按 `toolCallId` 幂等恢复，不能再次应用已成功 patch。
- 对外请求设置唯一非敏感 request ID；本地日志只记录 ID、状态、耗时和脱敏 provider profile ID。
- Responses adapter 在兼容时默认请求 `store: false`；中转站是否实际执行该语义属于其自身数据政策，SpotPatch 不作保证。

## 数据与信任边界

启用 AI 后，以下数据可能发送到配置的中转站及其上游模型：

- 每个已选目标各自的修改说明及其稳定顺序。
- 经过清洗和预算裁剪的页面、React、DOM、CSS 和源码上下文。
- Agent 按需读取的其他允许源码片段。
- 本地工具的有界结果、Diff 诊断和检查摘要。

默认不是“上传整个项目”，但 Agent 可能为完成任务读取多个相关文件。首次使用每个 provider profile 前，UI 必须明确显示 provider label、远程传输事实和“中转站数据政策由用户自行确认”，并取得本次 Vite 会话的显式同意。

Key 和源码发送给中转站意味着用户信任该服务。SpotPatch 无法验证中转站是否记录、训练、转售、二次转发或按其声明删除数据；不得把官方 OpenAI 数据政策描述成第三方中转站政策。

provider 输出、模型自然语言和工具调用都视为不可信输入。本地文件授权永远不能由 provider capability、模型名、系统 Prompt 或用户“自动执行”选项扩大。

## 错误与诊断

provider adapter 必须把外部错误归一为本地协议的稳定错误码，不向浏览器透传：

- 原始响应 body。
- Authorization 或自定义 header。
- Base URL query、上游 host 链和内部代理信息。
- provider SDK 堆栈。
- request 中的源码、Prompt 和工具结果。

诊断 UI 可以展示 provider/model label、协议、能力状态、request ID、HTTP 状态类别和建议动作；具体交互由 UI 规范定义 (见 doc-id:10-ui-diagnostics)。

## Codex CLI 与其他 provider

Codex CLI、Claude Agent SDK、GitHub Copilot SDK 或本地模型可以在后续作为新的 provider/executor adapter 接入，但不属于 `openai-compatible` profile，也不能复用其凭据字段冒充兼容。

新增 adapter 必须输出同一内部模型事件，并继续使用同一个本地 Agent 工具和 Git 安全执行层 (见 doc-id:16-ai-agent-execution)。因此 provider 可替换不等于工具权限可替换。

## 一手依据

- [OpenAI Function Calling](https://developers.openai.com/api/docs/guides/function-calling)：应用声明工具、模型返回工具调用、应用执行并关联工具结果；严格 Schema 应显式启用。
- [OpenAI Streaming Responses](https://developers.openai.com/api/docs/guides/streaming-responses)：Responses 使用 SSE 语义事件；Chat Completions 也可流式返回，但事件模型不同。
- [OpenAI Apply Patch](https://developers.openai.com/api/docs/guides/tools-apply-patch)：补丁宿主仍负责路径校验、备份/隔离、错误处理和原子性。
- [OpenAI API Authentication](https://platform.openai.com/docs/api-reference)：API Key 必须在服务端从环境变量或密钥管理系统加载，禁止暴露到浏览器。
- [Vite Env Variables and Modes](https://vite.dev/guide/env-and-mode)：`VITE_` 前缀变量会暴露到客户端构建，不能保存敏感 Key。

## 完成标准

- 用户可以通过 Base URL、环境变量 Key 和 model profile 连接严格兼容的中转站。
- Responses 和 Chat Completions capability probe 都有成功、协议缺失、工具缺失、畸形流、401、404、429、5xx 和超时测试。
- Key 在虚拟模块、浏览器请求、事件、日志、错误、子进程环境和生产产物中的泄漏均为 0。
- 浏览器伪造 URL、模型名、环境变量名和 provider header 全部被服务端拒绝。
- 不支持工具调用的模型只能降级到 Prompt 流程，不能修改本地文件。
- provider 返回重复 tool call、恶意路径和超限数据时，本地 Agent 仍保持幂等和 fail-closed。

测试和真实中转站 smoke test 的门禁只在测试与验收规范中定义 (见 doc-id:12-testing-acceptance)，本方案受 provider 与凭据相关 ADR 约束 (见 doc-id:15-risks-adr)。
