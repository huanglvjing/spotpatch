# Next.js 构建转换与源码定位

## 责任边界

本文只定义 Next 构建器如何承载通用 source marker 与 data-flow transform。marker 语义仍引用 (见 doc-id:04-vite-plugin)，数据链路证据引用 (见 doc-id:data-flow-13-beta-implementation)，源码来源与置信度引用 (见 doc-id:06-source-resolution)。公共编译内核只有 `@spotpatch/compiler`；Next 禁止复制 Vite 的 parser、anchor、请求识别或注入逻辑。

## 转换模式与构建目标

Loader 使用闭合枚举而不是互相影响的布尔开关：`source`、`data-flow`、`source-and-data-flow`。框架组合层按构建目标建立互斥规则：

| 构建目标 | `.jsx/.tsx` | `.js/.ts` |
| --- | --- | --- |
| 浏览器 development | `source-and-data-flow` | `data-flow` |
| Node/Edge development | `source` | 不转换 |
| production | 不转换 | 不转换 |

服务端 JSX/TSX 仍注入 host marker，以支持 Server Component 输出的精确 DOM 坐标；data-flow recorder、component registry helper 与 invocation frame 只能进入浏览器模块。不能依靠源码中是否存在 `"use client"` 推断真实构建目标。

webpack 必须使用 Next 提供的 `isServer` 分支建立上述规则；Turbopack 必须使用互斥的 `browser`/`not browser` condition，不能让同一资源同时命中两种模式。公共 include/exclude 对 data-flow 覆盖 `.js/.jsx/.ts/.tsx`，source marker 仍只处理 `.jsx/.tsx`。

## 选择 Loader，而不是 Compiler 私有插件

- Turbopack 官方支持一部分 webpack Loader，但不支持 webpack Plugin。
- Next SWC Plugin 仍具有实验性和 WASM/版本维护成本。
- 自定义 Babel 配置会使项目退出默认 Next SWC；SpotPatch 不应改变宿主编译器选择。
- 现有 Oxc + MagicString transform 已能保持源码格式和高精度 map，抽成 Loader 的风险低于重写两套编译插件。

因此公共预览提供由 `@spotpatch/next` 内部引用的 CommonJS Loader entry；实际 AST 行为只来自 `@spotpatch/compiler` (见 doc-id:next-02-package-architecture)。

## Turbopack 输出契约必须实证

现有 SpotPatch transform 只给 JSX/TSX 增加 marker，输出仍可能包含 TypeScript 和 JSX；而 Turbopack 官方只接受 Loader 返回 JavaScript。不能仅凭 webpack Loader API 兼容就推断 Next 的内置 SWC 会在正确阶段继续处理该输出。

Gate N1 必须用真实 Next 15/16 fixture 证明以下任一成立：

1. SpotPatch Loader 在 `turbopack.rules` 中返回带 marker 的 TSX/JSX 后，借助受支持的 `as`/规则链仍会进入 Next 内置编译，并保持 Fast Refresh 和 source map；或
2. 官方支持的规则顺序允许 SpotPatch 接收/返回已编译 JavaScript，同时仍能可靠识别业务 JSX 的原始行列。

两者均不成立时 ADR-025 视为被否决，必须回到编译入口架构评审。禁止在未评审情况下自行转译 TypeScript/JSX、复制 Next SWC 配置、使用私有 Turbopack API，或发布 webpack-only 版本后声称完整 Next 支持。

### Gate N1 编译链实测结论

2026-08-09 的隔离实验在 macOS arm64 上验证了 Next 15.3.9/React 18.3.1 与 Next 16.3.0/React 19.2.8：不设置 `as` 时，返回仍含 TypeScript/JSX 的探针 Loader 在两版 Turbopack 中继续进入 Next 内置编译；对应 webpack `enforce: "pre"` 通道也通过 hydration、Fast Refresh、Edge 和 map 断言。该结果只证明锁定版本的本地编译链，不改变官方“Loader 返回 JavaScript”的公开约束，也不外推到其他 Next 版本。

实验同时证明两种构建器的 map source 基准不同：webpack 探针使用项目根相对 source，Turbopack 探针使用资源相对 source 后再由 Next 合成 indexed map。该差异属于 Adapter 翻译层，不能写进公共 compiler。2026-08-09 扩展的本地矩阵在四个开发组合中均完成 500 个生成 TSX 模块、8 路并发冷请求与暖 `.next` cache 重启，私有 Next 16 App Router 真实宿主也通过 Turbopack、webpack 与生产隔离；同一扩展套件随后在 Ubuntu/Node 22 required CI 通过并留存机器证据。因此 Loader 编译链 POC 的范围内结论为 `pass`。当前正式 Loader 已实现内部 Source Registration、epoch cache 和 fail-open，但其他 Gate N1/N4 项目仍未形成完整 required matrix，ADR-025 仍不能据此提升为正式支持。复现命令、机器证据和 CI run 唯一定义见 `experiments/next-adapter/CONCLUSION.md`。

## 编译阶段

### webpack 通道

- 仅在 `dev === true` 时追加 `enforce: "pre"` rule。
- rule 在构建器入口排除所有层级的 `node_modules` 与 `.next`；Loader/Sidecar 仍执行各自的路径与授权复核，入口过滤不能替代安全校验。
- rule 在客户端、Node server、Edge server 三类编译中保持幂等，以便 Server Component host JSX 也获得 marker。
- 不覆盖 Next `defaultLoaders`、devtool 或 React Refresh loader。
- Loader 返回 `code + source map`。当前公共预览作为 `enforce: "pre"` 运行并要求没有上游 map；若收到上游 map，会警告一次并原样 fail-open，绝不输出未经正确组合的错误 map。支持需要上游 pre-loader 的宿主前，必须实现并验证 map composition。
- 同一 webpack 配置对象通过进程内 `WeakSet` 保证只追加一次，不在宿主对象写私有字段，也不使用脆弱的 loader 路径字符串猜测。

### Turbopack 通道

- 使用 `turbopack.rules`，匹配受支持的 JSX/TSX 文件并排除 foreign/package output。
- Loader options 只能包含 plain primitive/object/array；公共 `RegExp` filter 必须序列化为受控 `{ source, flags }` 结构并在 Loader 内重建，不能直接传递实例。
- Loader options 必须包含本次 CLI 启动生成的非敏感 `registryEpoch`，使 Turbopack/webpack 持久 cache 不会在新 Session 复用旧 fileId；epoch 不是认证凭据。
- webpack filesystem cache 的 `version` 必须组合原 version 与 `registryEpoch`，且保持 Next 原 cache 类型和其余字段；实测 Next 16 webpack 只改变 Loader options 仍可能跨进程复用旧输出。禁止用删除宿主整个 `.next` 目录代替精确失效。
- 不依赖 Turbopack 未实现的 `emitFile`、`loadModule`、`importModule` 或完整 `fs` LoaderContext。
- 官方契约仍按 Loader 返回 JavaScript 理解；锁定版本下“无 `as` 返回 TSX 后继续进入内置编译”的实测行为必须由兼容矩阵持续守护，不能外推。500 模块、并发冷请求与暖 cache 重启已取得 macOS 与 Ubuntu/Node 22 required CI 证据，后续实现必须持续保留该门禁 (见 doc-id:next-08-testing-delivery)。

## 文件过滤

Next Adapter 在调用公共编译器前完成框架 ID 归一化：

1. 取得 Loader `resourcePath` 的真实绝对路径。
2. 拒绝 root 外路径、符号链接逃逸和 NUL。
3. 只处理公共 include 且不匹配 exclude 的扩展名。
4. 固定排除 `.next`、`node_modules`、SpotPatch 包产物、Next 内部生成模块和测试/故事/覆盖率产物。
5. 不按模块内容推断 Server/Client Component；由 bundler target 决定是否允许 data-flow，符合条件的 host JSX 始终可进入 source transform。
6. 只以 `<` 快速跳过明显无 JSX 文件，不能把它作为正确性判断。

Next 新增排除项只能在 Adapter 翻译层定义；共同排除与公共选项继续由公共配置维护 (见 doc-id:03-public-api-models)。

## Source Registration

Vite 插件可在同进程 Registry 同步登记路径；Next Loader 可能运行于多个 Loader worker，不能共享进程内 Map。当前公共预览采用内部注册通道：

1. Loader 使用 Sidecar launcher 只注入到 Node 子进程的内部凭据建立请求。
2. Loader 先由公共 compiler 生成不可变的 prepared instrumentation；同一 AST 结果同时供注册和最终编辑使用，禁止重复解析后产生两套 anchor。
3. 一次认证请求提交 `resourcePath` 和可选的 `{ sourceVersion, components[] }`；Sidecar重新执行 real root、文件类型、扩展名、过滤、大小、数量和当前磁盘 sourceVersion 授权。
4. Registry 对同一 `registryEpoch + 规范化路径` 在一次 Session 返回稳定 fileId，并原子替换该文件的 component anchors；并发重复登记合并，旧 HMR 版本不得覆盖新版本。
5. Loader 在原子注册成功并验证 epoch/fileId 后，才用同一 prepared instrumentation 注入 marker/data-flow；禁止先生成半成品再异步补登记。
6. 每个 worker 使用有界 LRU 缓存；仅 source 模式可缓存 `registryEpoch + path → fileId`。携带 data-flow anchors 时仍需按 `sourceVersion` 注册，不能用 fileId 缓存跳过 HMR 更新。
7. `source-and-data-flow` 注册失败时只允许回退到重新验证过的 marker-only 注册；`data-flow` 模式失败返回原模块。不得留下 helper import、幽灵 anchor 或与 Registry 不一致的 marker。

内部通道不是公共 HTTP 协议，不能被 Next rewrite 暴露 (见 doc-id:next-05-sidecar-protocol)。请求数量、冷启动成本和 worker 复用必须实测；若达不到预算，应优化批处理/缓存，不能放宽路径安全。

## Server Component 与 Client Component

Loader 对服务端模块只修改 intrinsic opening element，不注入浏览器代码：

```tsx
// Server Component 与 Client Component 均只增加开发期 marker
return <button data-spotpatch-source="session-file-id:line:column">Save</button>;
```

Server Component marker 经服务端渲染进入 HTML/RSC；Client Component marker经 hydration 保持。浏览器构建中的 data-flow helper 只登记 compiler 已识别的业务 component type 和请求 anchor，不修改 composite props。不得用 `cloneElement` 或运行时遍历补写 marker。RSC 降级和 React stack 语义 (见 doc-id:next-06-rsc-runtime)。

## Source map 与诊断

- compiler map 以原始项目相对 POSIX 路径为 source 并包含原始内容；Next Loader 在 Turbopack 通道把 source 基准转换为资源文件名，再交给 Next 合成。两者都不得包含 Sidecar临时路径或凭据。
- data-flow helper import 必须位于 hashbang 与全部 directive prologue 之后；`"use client"`/`"use strict"` 仍保持模块首部。webpack 真实宿主必须持续验证该顺序，不能只依赖 Turbopack 宽松行为。
- 当前 Loader 不猜测上游 map 组合；存在输入 map 时原样返回业务模块。无上游 map 的 webpack/Turbopack 路径已验证 Next overlay、Fast Refresh 和源码上下文仍指向业务源码。
- Loader 诊断统一使用脱敏前缀 `[spotpatch:next:loader]` 和稳定原因码；compiler 的 AST 警告仍由公共实现定义。
- 普通模式每个文件/原因只警告一次；debug 可记录耗时和缓存命中，但不得输出源码、绝对路径或内部 token。
- parser/marker 失败一律 fail-open；路径注册安全失败不得伪造 fileId。

## 兼容冲突

下列组合必须有 fixture，不能依赖主观推断：

- 自定义 webpack rules、Babel 配置、MDX、React Compiler、styled-components/emotion compiler 选项。
- `src`/根目录布局、Monorepo 外层 root、symlink workspace 与 `transpilePackages`。
- `next/image`、`next/link`、Portal、lazy/dynamic、Suspense、RSC 导航。
- Windows 盘符/大小写、POSIX 路径、查询后缀和虚拟模块 ID。
- HMR 行号变化、文件重命名、删除、Registry 失效、Sidecar 崩溃、Next dev cache 与 CLI Session 重启。

未通过组合应显示为明确“不支持/冲突”，禁止静默跳过后仍显示 exact。
