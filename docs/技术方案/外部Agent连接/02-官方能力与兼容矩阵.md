# 外部 Agent 连接：官方能力与兼容矩阵

## 调研纪律

本页只引用协议或产品官方资料，调研日期为 2026-08-23。Agent 产品、CLI 参数、MCP SDK 和预览能力会变化，因此：

- 文档中的“支持”只表示官方存在该能力，不表示 SpotPatch 已通过兼容测试；
- 发布支持必须绑定 required fixture 中锁定的正式版本，不能绑定“latest”；
- SDK 的确切版本只能在 POC 当日选择并锁定，不能把调研时版本复制成长期范围；
- beta、research preview、experimental 能力不得冒充跨宿主公共保证；可以作为默认关闭、可整层移除且有独立 Gate 的宿主专属能力；
- 搜索结果、博客和社区插件不得替代官方文档与真实客户端 E2E。

## 一手依据

### MCP

- [MCP Architecture](https://modelcontextprotocol.io/docs/learn/architecture)
- [MCP Server Resources](https://modelcontextprotocol.io/specification/draft/server/resources)
- [MCP Server Tools](https://modelcontextprotocol.io/specification/draft/server/tools)
- [MCP Transports](https://modelcontextprotocol.io/specification/draft/basic/transports)
- [MCP TypeScript SDK 官方仓库](https://github.com/modelcontextprotocol/typescript-sdk)

确认事实：MCP 将 host、client、server 分层；stdio 与 Streamable HTTP 是标准 transport；tools 由模型/宿主调用，resources 由客户端读取。Resource update/subscription 只通知“资源变化”，交互和注入方式由 host 决定，不能推导为所有客户端都会把新内容主动加入现有对话。

### Claude Code

- [Claude Code MCP](https://code.claude.com/docs/en/mcp)
- [Claude Code Channels](https://code.claude.com/docs/en/channels)
- [Claude Agent SDK MCP](https://code.claude.com/docs/en/agent-sdk/mcp)
- [Claude Code CLI Reference](https://code.claude.com/docs/en/cli-reference)

确认事实：Claude Code 可连接本地 stdio MCP；标准 MCP 是查询式交互。Channels 可以让本地 stdio MCP server 向**正在运行且已启用该 Channel**的 Claude Code 会话发送 `notifications/claude/channel`。自定义 server 必须声明 `experimental["claude/channel"]`；事件正文是字符串，可选 `meta` 只能使用字符串值和字母/数字/下划线键。Channel 当前仍是 Research Preview：裸 server 使用 `--dangerously-load-development-channels server:spotpatch` 开发加载；组织 `allowedChannelPlugins` 只接受 plugin + marketplace 形式，不能直接批准裸 server。开发参数按 entry 绕过 plugin allowlist，但组织级 `channelsEnabled` 总开关仍可阻断。关闭的会话不能被唤醒；若依赖后台 Agent View，未 pin 的空闲进程还可能被 supervisor 停止，因此 ready 必须来自当前真实存活连接。

`mcp.notification()` resolve 只证明消息写入 transport。官方没有 Channel notification ACK；未启用、策略阻断等情况可能静默丢弃。Claude 忙时事件由宿主排队，可能在下一轮合并呈现。SpotPatch 因此只把它作为实验性唤醒提示，以 Broker 中的 Handoff 为事实源，并要求 Agent 通过工具上报 `working/completed/failed`。

SpotPatch 明确避免协商到 `2026-07-28`：Claude Code 新 MCP runtime 的该版本当前不承载 Channel 消息。宿主进程保持 `MCP_PROTOCOL_NEGOTIATION` 未设置或设为 `legacy` 均可保留旧握手；SpotPatch 启动说明推荐显式 `legacy`，Channel server 还要核对实际 initialize 协议并对不兼容版本 fail closed。只给 server 子进程改环境而不影响宿主真实握手不能算完成该约束。

### Cursor

- [Cursor MCP](https://docs.cursor.com/context/model-context-protocol)
- [Cursor CLI Overview](https://docs.cursor.com/en/cli/overview)
- [Cursor CLI Parameters](https://docs.cursor.com/en/cli/reference/parameters)

确认事实：Cursor 支持 MCP server，覆盖 stdio、SSE/Streamable HTTP 等配置形态；IDE 与 CLI 能消费 MCP。Cursor CLI 支持非交互、结构化输出、恢复等能力，但版本与写入权限语义必须独立验证，不能替代通用 MCP 交接。项目级 MCP 配置适合首版的一次设置目标。

### Codex

- [Codex MCP](https://developers.openai.com/codex/mcp/)
- [Codex App Server](https://developers.openai.com/codex/app-server/)
- [Codex Non-interactive Mode](https://developers.openai.com/codex/noninteractive/)

确认事实：Codex 支持 stdio 和 Streamable HTTP MCP，并提供项目级配置。stdio MCP 配置可以通过 `env_vars` 选择性转发启动 Codex 进程中的环境变量，不需要将具体值写入配置；`enabled_tools` 是 server 级 tool allowlist，`disabled_tools` 在其后应用。Codex App Server 是官方提供的客户端 deep-integration interface；默认使用换行分隔 JSON 的 stdio 协议，线上的 JSON-RPC 形态不携带 `jsonrpc: "2.0"`。当前 `app-server` command 及 WebSocket transport 仍标为 experimental，官方不建议用于 production workload。客户端必须先完成 `initialize` / `initialized`，再使用 `thread/start` 和 `turn/start`；匹配的 `turn/start` 成功响应只证明请求被接受，`turn/started` 才证明 turn 开始运行，`turn/completed.params.turn.status` 只证明协议终态，不证明指定代码修改或检查已经成功。`turn/steer` 只适用于已运行 turn；SpotPatch 首版不自动使用它，也不把两个独立点击合并为一个 turn。

锁定 `codex-cli 0.149.0` 生成 Schema 与真实 stdio POC 还确认：server notification envelope 可带 `emittedAtMs`；`thread/start.config` 可临时注入 `mcp_servers.spotpatch`，无需写项目配置即可达到 MCP `ready`；App Server 会把 cwd 从附加 `sandbox.writableRoots` 中归一化掉并另报 `runtimeWorkspaceRoots`。2026-08-24 的独立无 turn 真实预检进一步完成 `mcpServerStatus/list` 与 `mcpServer/tool/call(spotpatch_list_sessions)`，实际只暴露 Session-list 并只返回精确选定 Session。以上均是锁定版本合同与实测，不外推为其他版本事实，因此 adapter 继续精确版本门禁和 fail-closed 解析。

App Server 是 Codex 专属的深度嵌入协议，不能成为 Claude/Cursor 的公共连接层，也不能被描述为向任意已打开的 Codex UI 对话注入消息。SpotPatch 主动模式拥有一个专用 App Server 进程和 thread；可写 sandbox 必须由用户在 Node CLI 明确开启，浏览器不能选择 cwd、模型、审批或 sandbox。

## 共同能力与关键差异

| 能力 | Claude Code | Cursor | Codex | SpotPatch 判断 |
| --- | --- | --- | --- | --- |
| 本地 MCP stdio | 官方支持 | 官方支持 | 官方支持 | 跨宿主上下文基线 |
| MCP tools | 支持 | 支持 | 支持 | `get/wait/list/ack` Inbox 基线 |
| MCP resources | 支持，展示由宿主决定 | 支持，展示由宿主决定 | 支持，展示由宿主决定 | 只做可选发现，不作为交付保证 |
| Resource update 自动入对话 | 无跨宿主保证 | 无跨宿主保证 | 无跨宿主保证 | 禁止宣传为通用 push |
| 真正外部事件/turn 入口 | Channels，Research Preview | 截至调研日无等价、已验证的稳定入站入口 | App Server `turn/start` | Claude/Codex 独立 adapter；Cursor 保持 Inbox |
| 非交互 CLI | `claude -p` 等 | Cursor CLI | `codex exec` | 后续显式 launch adapter |
| 线程/会话深度嵌入 | Agent SDK/CLI 专属 | CLI/IDE 专属 | App Server | 不进入公共 Handoff Schema |
| 项目级 MCP 设置 | 支持 | 支持 | 支持 | 设置生成器优先项目 scope |

## 连接方式评估

| 方案 | 延迟 | 兼容性 | 安全/维护成本 | 结论 |
| --- | --- | --- | --- | --- |
| MCP stdio tools | 低；本机进程通信 | 三个目标客户端共同支持 | 低；无需暴露远程服务 | **上下文与 Inbox 基线** |
| MCP resource + subscription | 潜在低 | host UI 行为不一致 | 中；容易误解为主动消息 | 可选增强，非门禁 |
| MCP Streamable HTTP | 低 | 官方协议支持但本地配置差异更大 | 需独立认证、会话和端口 | 首版不开放；stdio 已足够 |
| 通用 CLI JSON | 低 | 任何脚本可消费 | 需稳定退出码/超时 | **首版后备** |
| 直接启动任意 Claude/Cursor/Codex CLI | 启动较慢 | 厂商差异大 | 高；写权限、审批、恢复、版本 | 禁止通用命令模板；逐厂商另立 Gate |
| Claude Channels | 很低、可主动事件 | 仅运行中且启用 Channel 的 Claude；预览 | 中高；无 ACK、plugin allowlist/裸 server 开发开关、协议易变 | **实验性 Claude adapter** |
| Codex App Server | 低、事件丰富 | SpotPatch-owned Codex runtime/thread | 中高；完整 client、子进程、权限和事件状态机 | **实验性 Codex adapter** |
| 公网远程 MCP | 网络相关 | 可覆盖 web host | 极高；认证、隧道、源码外发 | 不符合首版 local-first |
| 剪贴板 Prompt | 人工延迟 | 通用 | 已有、最简单 | 保留为零配置降级 |

## 计划兼容矩阵

兼容必须把“能读取 Inbox”和“能被一次点击主动触发”分开。当前存在本机实现不表示对应宿主已经完成真实兼容测试：

| 宿主 | 首版等级 | 目标入口 | 约束 |
| --- | --- | --- | --- |
| Claude Code 本地 CLI/IDE 体验 | required | MCP stdio tools | 正式版、项目 root/cwd、工具超时实测；这是 Inbox 能力 |
| Cursor IDE | required | MCP stdio tools | 项目级 MCP 配置、审批 UI 实测 |
| Cursor CLI | observed | 同一 MCP server | beta/权限变化不阻断 IDE 主链路 |
| Codex CLI / IDE extension | required | MCP stdio tools | 项目级 `.codex` 配置和审批实测 |
| Codex App | observed | 若能消费同一 MCP 则观察 | 不把 SpotPatch-owned App Server thread 冒充现有 App 对话 |
| ChatGPT 网页版 | unsupported | 无本地 stdio | 浏览器不能直接启动本机 MCP；远程 MCP 另立项 |
| 原始 OpenAI/Anthropic 模型 API | not-an-agent-host | 无 | API 本身没有本地工作区、编辑器和审批；需由上层 Agent 宿主承载 |
| 其他支持 MCP stdio 的 Agent | compatible-by-protocol | MCP tools | 只承诺协议，不承诺未测试产品 UI |
| 不支持 MCP 的本地工具 | fallback | CLI JSON | 调用方自行管理进程与编辑权限 |

主动适配矩阵独立如下：

| 宿主 | 主动入口 | 当前成熟度 | 可验证上限 |
| --- | --- | --- | --- |
| Claude Code | Channel-aware MCP server | experimental / local-validation | transport 已写入；模型开始/结束依赖显式状态工具 |
| Codex | `codex app-server` | experimental / local-validation | `turn/start` 接受、`turn/started`、`turn/completed` |
| Cursor | 无已验证入口 | inbox-compatible | published / picked-up，不主动唤醒 |
| 其他 Agent | 逐 adapter 评估 | 未实现 | 只按该宿主官方合同和真实 E2E 声明 |

`ChatGPT 网页版` 的结论是基于 transport 形态的工程推断：本地 stdio 要求宿主在用户机器启动子进程，网页本身不具备该能力。若未来通过远程 MCP 接入，必须重新评估公网身份、项目内容传输和权限，不得复用首版安全声明。

## 为什么 MCP 不能单独完成“点击即主动推入对话”

标准 MCP 的通用部分能可靠完成：

1. Agent 调用工具获取当前上下文；
2. Agent 调用有界等待工具，在请求未完成时接收下一次发布；
3. Client 订阅资源变化并决定如何展示。

它不能跨宿主保证：

- 没有进行中的工具调用时，server 可把任意用户消息插入当前对话；
- 收到 resource notification 后，host 会自动触发模型；
- 多个打开对话中应该唤醒哪一个；
- Agent 会自动获得写权限或开始编辑。

所以 Generic MCP 产品文案必须使用“发布交接”“等待下一次交接”“连接器已取走”，不能使用“已推送到所有 Agent”“Agent 正在修改”。只有已经取得目标 dev Session 主动 lease 的厂商 adapter 才能使用“派发”；该 lease 只约束 SpotPatch 管理的主动 adapter，不阻止普通 MCP Connector 读取同一 Inbox。`working/completed` 还必须有该协议的结构化事件或 Agent 显式状态上报，且 `completed` 只是协议/上报终态。完整状态边界见 (见 doc-id:external-agent-09-active-dispatch-adapters)。

## POC 必须复核的易变事实

- 三个客户端的正式版 MCP 配置文件、项目 scope、启动 cwd 和 roots 行为；
- tool call 默认/最大超时、取消时是否终止 stdio server 请求；
- 结构化 tool result 的大小上限和长文本截断方式；
- 客户端是否并发调用工具、是否会重复调用和如何展示错误；
- resource URI、subscription、prompt 的实际可发现性；
- MCP server stderr 如何显示，是否可能把敏感诊断暴露到聊天；
- 客户端升级后是否保留项目级设置和审批默认值。
- Claude Code 锁定版本在开发 Channel 参数下能否连续接收两次事件、关闭/忙碌/组织策略下的实际表现，以及 legacy MCP 协议是否被保持；
- Codex 锁定版本生成的 App Server Schema、初始化顺序、server request fail-closed、thread/turn 状态、进程退出和连续两次 `turn/start`；

复核结果、版本与证据必须进入 (见 doc-id:external-agent-08-testing-delivery)；任何 required 客户端不支持基线工具时，先回到 ADR 评审，不能偷偷引入厂商分叉。
