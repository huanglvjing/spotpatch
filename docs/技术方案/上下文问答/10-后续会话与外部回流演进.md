# 上下文问答：后续会话与外部回流演进

本文只预留兼容方向，不授权首阶段实现。未进入对应 Gate 前，不创建空 DTO、UI 按钮、adapter stub 或 feature flag。

## 连续追问

首阶段一个 Job 只有一问一答。后续追问需要显式 `AskSession v2`：

```ts
interface AskSessionRef {
  readonly sessionId: string;
  readonly selectionId: string;
  readonly contextHash: string;
  readonly nextTurn: number;
}
```

演进原则：

- 用户点击“继续追问”才创建/延续 session；普通 New question 仍是独立 Job；
- 每 turn 仍是单问题、单答案和独立 source refs；
- selection/context 变化时不能静默延续，必须提示“更新上下文并开始新会话”或 fork；
- 总 turn、字符、文件、TTL 和 token 有会话级上限；达到后显式开始新会话，不自动 compaction 隐藏上下文丢失；
- Key 可复用 Provider 状态或重放有界结构化摘要；Codex 可 resume 同一 ephemeral/live thread，但两者必须产生相同产品语义；
- 转 Change 绑定具体 answer turn，不含整个未审阅历史。

这仍不是长期聊天历史。首个 follow-up 版本建议只在当前页面内存保留，dev Session 结束清除；持久历史需要独立隐私、删除、迁移和存储 ADR。

## Claude Code 答案回传

候选协议是在现有 Channel MCP host 增加专用只读结果 tool：

```text
spotpatch_submit_answer({
  cursor,
  answer: { blocks, citations, warnings }
})
```

要求：

- inbound Channel 只携带 opaque cursor/selection summary，正文仍从精确 Handoff/Ask snapshot 获取；
- tool 参数使用与 AskAnswerDraft 同源的严格 Schema，cursor/lease/Session/TTL 精确关联；
- 每 cursor 只接受一个 terminal answer；重复同 payload 幂等，不同 payload 冲突；
- reply tool 成功才是“答案回 SpotPatch”证据；Channel notification write/Claude turn end 都不是；
- Claude 会话仍由宿主权限控制。要宣称只读，必须有工具/permission mode 的真实证据；仅在 instructions 中写“不要修改”不够；
- Channel 是 Research Preview，版本、组织策略、会话存活、sender gating、迟到/离线/繁忙队列都进入 required matrix；
- 失败时保持 Inbox/Key/Codex 可用，不把 lifecycle result tool 混成 answer tool。

若无法证明宿主零写，Claude 可以作为“外部回答，宿主权限自理”的独立 capability 展示，但不能使用 Managed Read-only 标识。

## Cursor Inbox/CLI 回传

两条路线必须二选一并分别命名：

### Cursor Inbox answer

Cursor 用户/Agent 通过 Generic MCP 获取 Ask snapshot，再显式调用 `spotpatch_submit_answer`。它是 pull/inbox，不承诺点击即推入当前 IDE 对话。证据只覆盖 published、picked-up、answer-reported；没有 tool call 就没有答案。

### Managed Cursor CLI answer

SpotPatch 启动官方 Cursor Agent CLI 的 non-interactive JSON/stream-json 模式，解析 terminal result。由于官方参数说明 print mode 拥有 write/bash 工具，必须先证明一个锁定版本的 OS 只读 sandbox、cwd、网络、配置/规则隔离、取消和进程树清理。没有这组证据不得命名 Managed 或 Read-only。

两条路线不能共享一个模糊 `cursor` executor ID，也不能从 IDE 安装状态推断 CLI/API 可用。

## 跨页面 Ask 会话

当前 selection 已通过 sessionStorage 支持同标签页、同源、同 dev Session 的跨页面草稿；首阶段 Ask 不使用该能力保存问题/答案。后续跨页面需要：

- 存储键只含 dev Session 和随机 ask session ID，不含 token/绝对路径；
- 存储结构有版本、最大字节、turn 数、expiresAt、selection/context hash；
- 默认只保存 question、AnswerResult 的安全投影和 source IDs；不保存源码正文、Provider/Codex ID、Key 或原始 Prompt；
- 每页恢复后向 Node 验证 session/result 尚在且 source refs current；Node 重启/TTL 到期显示过期，不猜恢复；
- 页面 A 运行时页面 B 不并发接管；使用单 owner lease/BroadcastChannel 协调，同 tab history 导航不创建双 writer；
- 用户有明确“清除问答会话”，Start over 同时删除 storage 和 Node result；
- 生产无 storage key 和恢复代码。

跨页面不等于跨项目、跨浏览器、跨设备或长期历史。

## 协议演进

- 首阶段 `SpotTaskEnvelope v1` 的 `task.kind=ask` 保持单问题；追问使用新 endpoint/capability 或 v2，不给 v1 增加可选 history 导致语义漂移。
- `AskAnswerResult v1` 可被所有未来 executor 复用；厂商原始 ID 留在 Node 诊断，不进入公共结果。
- 外部回传使用独立 audience/lease/result Schema，不能复用 Browser cookie 或把 cursor 当认证。
- capability 必须逐项声明 `singleTurn`、`followUp`、`answerReturn`、`readOnlyProven`、`crossPageResume`；UI 按证据呈现，不按厂商名猜能力。

## 后续 Gate 顺序

```text
E1 当前页面连续追问（Key + Managed Codex 一致）
→ E2 Claude 两向回传真实会话 Gate
→ E3 Cursor Inbox 回传 Gate
→ E4 Cursor CLI 只读 POC（若产品仍需要）
→ E5 跨页面 Ask 会话
→ E6 评估是否需要可选长期历史
```

每一步都必须先更新需求、协议、安全、UI、测试和 ADR，再编码。不能为了“以后可能用”在首阶段保留未使用字段或死代码。
